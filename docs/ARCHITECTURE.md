# blirp architecture

blirp is a free, open-source, self-hostable workspace for CLI coding agents (Claude Code, Codex, opencode, pi, Gemini CLI, Cursor CLI, Amp, Aider, DeepSeek Harness `dsh`, or any other command). It runs the real, unmodified agent TUIs inside terminal panes, tracks every session, and gives every new session automatic memory of prior work in the same project. Machines can pair to one self-hosted hub so memory follows the user across Windows, macOS and Linux.

This document is the contract. Code must match it; if code needs to diverge, update this file in the same change.

## 1. Principles

1. **Ingest, don't scrape.** Agents already persist structured transcripts. blirp tails those native stores. PTY output is only used for the live terminal and activity/status heuristics.
2. **Agents stay unmodified.** blirp never proxies model traffic and never stores agent credentials, except a Claude Code login token the user explicitly hands it for headless machines (§7). It only launches the CLI with extra flags/env, and installs hooks/MCP config.
3. **Projects are folders, not repos, and need not be folders at all.** A project is any set of directories, or none: a project without folders works in a blirp-managed workspace per machine (a design tool's MCP server, notes). Git is optional and only unlocks git features (branch display, diff panel, optional worktree per session). A folder with no `.git` is a first-class project. Sessions that are part of no project are chats (§5), kept apart from projects.
4. **Local first.** Everything works standalone with no hub and no network. The hub is an optional replica/aggregator.
5. **One binary.** `blirp` is the daemon, CLI, hook handler, MCP server and hub. The desktop app is a thin Tauri shell around the web UI served by the daemon. The web portal is the same SPA.
6. **Never break the agent.** Hooks must exit 0 fast (hard 2 s budget) even if the daemon is down. Memory injection failures degrade to "no memory", never to a broken session.

## 3. Runtime layout

Data dir `BLIRP_HOME`, default `~/.blirp` on every OS (Windows: `%USERPROFILE%\.blirp`).

```
~/.blirp/
  config.toml        user config (see §12)
  blirp.db           SQLite (WAL) - all state
  runtime.json       {pid, port, token, version, started_at}; written by daemon, mode 0600
  identity.key       iroh secret key, 64 hex chars (0600); created on first start
  tls/cert.pem, tls/key.pem   self-signed LAN portal certificate (hub, key 0600)
  daemon.lock        single-instance lock (OS file lock held by the daemon)
  logs/blirpd.<date>.log   rolling logs (tracing-appender, daily, keep 7); stderr gets a copy only when it is a terminal
  logs/desktop.<date>.log  desktop shell log (same rotation); launchd.log: LaunchAgent stdout/stderr (macOS)
  worktrees/<project-id>/<name>/   optional per-session git worktrees
  workspaces/<project-id>/         working folder of a project without folders (§5), created 0700 with its
                                   first session on this machine; never synced
  launch/<session-id>/             per-launch generated files (claude settings.json, mcp.json, memory.md)
  uploads/<session-id>/<ms>-<name> files pasted or dropped into that session's terminal (§6); 0700/0600,
                                   removed with the session and after 7 days
  distill/run-*/                   summarizer scratch dirs (§9), removed after each run
  secrets/claude_oauth_token       optional Claude Code login token (§7); dir 0700, file 0600; never in the DB
  files/blobs/ab/cd/<hash>.zst     project file contents on the hub (§10a); files/tmp/ partial uploads,
                                   files/dl/ partial downloads (every machine)
```

`runtime.json` + the token authenticate every local client (Tauri shell, hooks, MCP stdio shim, CLI). The daemon binds `127.0.0.1:<port>` (default 47770). It and the LAN portal bind exclusively (`SO_EXCLUSIVEADDRUSE` on Windows, where another program could otherwise bind a more specific address on the same port, e.g. `127.0.0.1` under the portal's `0.0.0.0`, and receive its connections). A taken port fails the start with an error naming the program that holds it when the OS tells (never a silent move to another port, which would leave the known address to whoever holds it); `daemon.port = 0` explicitly picks a free port. The actual port is in runtime.json.

## 4. Processes

- `blirp daemon` - long-running per-user process. Owns PTYs, ingest watchers, memory jobs, SQLite writer, local HTTP/WS API, and (optionally) the iroh sync endpoint and LAN portal (hub). Single instance enforced by a lock file; a second daemon exits 0 when the lock holder answers health checks (so launchd `KeepAlive.SuccessfulExit = false` and systemd `Restart=on-failure` stop restarting a duplicate), else 1, and `--detach` keeps waiting while another starter's daemon holds the lock. `--detach` starts it in the background (from an AppImage mount: the install receipt's CLI instead when the receipt records this same version, since the daemon serves the UI and owns the schema, and since the daemon outlives the mount and its per-session hooks and MCP entries name its own binary) with `BLIRP_HOME` as its working directory (never the caller's folder, which it would otherwise keep in use) and without any handle of its caller: no std streams, and on Windows `CreateProcessW` with `bInheritHandles = FALSE` (a `Command` passes every inheritable handle on, so a caller reading a pipe it handed down would wait for the daemon to stop).
- `blirp hook <agent> <event>` - short-lived; reads hook JSON from stdin, POSTs to daemon, prints injection output where the agent supports it. Always exits 0.
- `blirp mcp` - stdio MCP server spawned by agents. Reads the local SQLite directly in read-only mode for queries; writes (e.g. `mem_record`) go through the daemon API.
- `blirp <cli>` - `status`, `start` (unless a daemon answers: through the autostart service when one is installed for this `BLIRP_HOME` (launchd `kickstart`, `systemctl --user start`; the unit's `BLIRP_HOME`, else the default data dir, must match), so the service keeps supervising it, else `daemon --detach`; used by `blirp`/`app`, `blirp update`, the install scripts and the desktop app), `worktrees list|prune` (see `POST /api/sessions/:id/worktree/remove`), `stop` (first `systemctl --user stop` when a unit is installed for this `BLIRP_HOME`, which also cancels a pending restart; then graceful `POST /api/daemon/shutdown`; if the daemon still holds `daemon.lock` after 15 s, or does not answer, the pid from runtime.json is killed; the lock, not the pid, decides whether a daemon runs), `logs [-n N] [-f]` (end of the newest `logs/blirpd.<date>.log`; `-f` follows it across the daily rotation), `open` (opens UI/portal in browser with a login link), `mem search|brief|show`, `sessions`, `pair`, `hub enable|disable|invite|status|setup` (setup: §18), `backup <file>` (§18), `devices list|revoke`, `service install|uninstall|status`, `hooks install|uninstall|status`, `skills install|uninstall|list` (§9), `agents set-token|clear-token claude` (§7), `doctor`, `update [--check] [--version X]` and `uninstall [--purge] [--yes]` (§17), and `app` (also `blirp` with no command: `start`, then open the desktop app if installed, else the browser login link; in an SSH session (`SSH_CONNECTION`/`SSH_TTY`) or on Linux without `DISPLAY`/`WAYLAND_DISPLAY` it only prints the URL, a login link for a port forward and the portal hint).
- Desktop app - on launch ensures the daemon is running (spawns sidecar `blirp start` if not), reads runtime.json, opens a window at `http://127.0.0.1:<port>/#token=...`; the SPA stores the token for its origin and removes it from the URL (§11). Closing the window does not stop the daemon or sessions.

Autostart: `blirp service install` registers per-user autostart: macOS LaunchAgent `~/Library/LaunchAgents/dev.blirp.daemon.plist` (`blirp daemon`, `KeepAlive.SuccessfulExit=false`), Linux `systemd --user` unit `blirp.service` (`Restart=on-failure`, `enable --now`; headless hubs also need `loginctl enable-linger`, which `hub setup` handles, §18; `systemctl --user` gets `XDG_RUNTIME_DIR=/run/user/<uid>` when it is unset and that manager's bus exists, e.g. after `sudo -iu`), Windows `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` value `blirp` = `conhost.exe --headless "<blirp.exe>" daemon --detach` (no console window). The unit records the absolute binary path and, on macOS/Linux, the installing shell's `PATH` and an explicit `BLIRP_HOME`. Install is idempotent (an existing daemon is left running and the service takes over at next login); uninstall removes exactly that entry; on Windows and Linux a running daemon keeps running, on macOS unloading the LaunchAgent (`launchctl bootout`) stops the daemon it started, and the command says which happened. Never a system service (it would not see the user's agent logins).

## 5. Data model (SQLite, `blirp-core::store`)

All ids are UUIDv7 strings unless stated. Every id a replicated change carries must be 1-128 chars of `[A-Za-z0-9_-]` (`is_safe_id`; ids name files such as `launch/<session>/` and arrive from other machines), checked when the row is written; `Paths::launch_dir` refuses any other id. Timestamps are integer unix milliseconds. Migrations are embedded and versioned (`PRAGMA user_version`). WAL mode, `foreign_keys=ON`, `busy_timeout=5000`.

All writes to replicated entities (`projects`, `project_paths`, `sessions`, `events`, `records`, `briefs`, `wiki_pages`, `resources`, `machines`) go through `Store::apply(Change)` which writes the row and appends to `outbox` in one transaction. One exception keeps the outbox from growing with every status flip: a session change that only moves between live statuses (starting/working/idle/waiting, plus `last_activity_at`) within 5 s of that session's last outbox entry writes the row and records `outbox_deferred(entity, key, due)` (migration 5) instead; the daemon's 500 ms status tick queues the then-current row once `due` passes (`Store::flush_deferred`), and any other change to the session (a final status, a title, tokens) is queued at once and clears the deferral. So at most one status-only entry per session per 5 s is replicated and the final state always is.

The outbox only exists for replication. A standalone machine queues nothing (`Store::set_replication(false)`, settings key `sync.outbox_off`, set at daemon start and on every role change; the outbox is emptied in chunks: nothing unpushed is lost, since pairing again queues the current state with its tombstones, and newer versions win). Becoming a hub or node turns queueing on and backfills: in that transaction every replicated row except events is queued (this machine's machine row, folders and sessions; all projects, records, wiki pages, resources, every brief version then the current brief; session and record tombstones), so the hub knows every session before any of its events; the events of this machine's sessions that exist at that moment (rowids up to the maximum then, later ones are queued as they are written) follow in resumable batches of 2 000 from the daemon's status tick (position and bound in the settings key `sync.backfill_events`, `[after, until]`). Shared rows are queued as this machine has them, possibly stale; they only win where they are newer (conflict rule, §10). Folders unregistered while standalone (or not yet pushed when the machine left: leaving pushes what is queued first, so only when the hub could not be reached) are not propagated; deleted records, sessions, wiki pages, resources and projects are (tombstones, or the `deleted` flag of a newer version). Entries are pruned once they can no longer matter (older than 5 s, which status coalescing reads): on a node, entries at or before its own last entry seen in an applied pull (they sit before every entry still to be pulled, so they can never be the "later own write" that makes a pull skip a remote one), and never past what the hub acknowledged (`own_seen` is the hub's claim); on a hub, entries already copied into `hub_log`. `hub_log` is what pulls read (a new node replays it from the start); two things keep it small (migration 9). Events are logged without their payload (`payload_json` is empty): the hub has every event it logged in `events` (append-only) and a pull reads it from there, so an event is stored once; one whose session was deleted since is left out of pulls (the delete follows it in the log). And the hub compacts it (`Store::compact_hub_log`, a background task a minute after the hub starts and then hourly, in write transactions of 1 000 rows): an upsert of a machine, folder or session (last writer wins by hub order) is dropped once a later upsert of the same row by its owner (which rewrites the whole row) is logged, except the row's first upsert (a session's events are only accepted once it exists); another machine's session write (a rename or move) only once that later owner upsert carries title and project edit times at least as new as its own. Markers of rejected or parked entries at or below the floor go once a row of the same origin with a higher `origin_seq` is at or below it too. Deletes, events and shared rows (projects, records, wiki pages, resources, briefs: the newest version wins by content, not by log order, and a brief carries its history row) are never compacted. Compaction only touches rows at or below the floor: the lowest pull position (the `after` of its last pull request, kept in `hub_pulls`) of the paired, non-revoked machines, 0 for one that has not pulled yet, the head when none is paired. An active node never reads below the floor again, so nothing changes for it. Each origin's row with the highest `origin_seq` at or below the floor is kept as a marker (payload emptied; only its origin gets it, as an own entry), so `own_seen` stays exact. A revoked machine does not hold the floor back and its cursor may fall behind it. That is safe because a machine pairs again only from standalone, which empties its outbox: everything it queues then is newer than anything it had logged, so the compacted rows could never have changed what its pulls skip or apply. A paired machine that never syncs again holds compaction back until it is revoked (revoking also forgets its position). A node whose cursor went back below a position it already pulled from and below the highest floor compacted so far (settings key `sync.hub_log_compacted`), e.g. after its database lost recent writes, could skip writes it must apply: the hub refuses that pull with the error `resync_required` (the node shows it as its sync error and retries); it has to leave the hub and pair again. The database file does not shrink (blirp never runs `VACUUM`); freed pages are reused. Nothing else may write those tables, except replication applying changes received from other machines (`Store::apply_remote` and the hub/node batch paths in `store::sync`), which write the row without queueing it again (no echo).

The machine id is the iroh endpoint id from `identity.key`. Installs that predate the identity used a local uuid; on first start the daemon rebinds that uuid to the endpoint id once (`Store::rebind_machine`: this machine's folders and sessions move, the old machine row is dropped with `Change::DeleteMachine`, all through the outbox). Migration 2 adds the indexes replication needs (`outbox(entity, key, origin_seq)`, `hub_log(origin_machine, hub_seq)`); migration 9 adds `hub_log(entity, key, hub_seq)` for upserts (compaction).

### Project resolution

`resolve_project(machine_id, cwd)`:
0. Canonicalize cwd. A folder inside `BLIRP_HOME/workspaces/<project id>` belongs to that project when it is live (`NonProjectDirs::workspaces`; a removed project's workspace is Chats), before every other rule.
1. Walk up to find the nearest registered `project_paths.path` that is a prefix; if found, use it.
2. Else, if cwd is inside a git work tree, use the git top-level as the project root; if another machine already has a project with the same normalized `git_remote`, attach this path to that project; else create a project named after the folder.
3. Else (no git): for a session the user starts in blirp, cwd itself becomes the project root (they picked the folder). For sessions blirp did not start (ingest, hooks; `NonProjectDirs::from_process`, `auto`) only an actual project folder does: the nearest folder from cwd up with a project marker (`PROJECT_MARKERS` in `store/projects.rs`: build manifests such as `package.json`, `Cargo.toml`, `go.mod`, `pyproject.toml`, `requirements.txt`, `pom.xml`, `*.sln`, `*.csproj`; `.hg`, `.svn`, `.jj`; agent setup `.mcp.json`, `AGENTS.md`, `CLAUDE.md`; matched case-insensitively), searched up to the first folder the scratch rules below cover (home at the latest). Without one the session is a chat: it goes to this machine's Chats project. Exceptions for every session: the user's home directory, its ancestors and filesystem roots are never auto-registered as project roots; sessions there are chats. For sessions blirp did not start the same holds for scratch folders, checked on the root steps 2 and 3 picked (so a Codex worktree under `~/.codex/worktrees` still resolves to its main repo first): anything inside the temp folder (`std::env::temp_dir`; on unix also `/tmp` and `/var/tmp`), the Windows folder (`%SystemRoot%`), a hidden folder directly under home (`~/.codex`, `~/.claude`, `~/.blirp`, tools' profile dirs), the Desktop, Downloads and Documents folders themselves, or a Codex desktop chat folder `<Documents>/Codex/<YYYY-MM-DD>/...` (the app makes one per project-less chat), where `<Documents>` is `~/Documents` and the OS's Documents folder (Windows `FOLDERID_Documents`, which may be redirected to OneDrive; elsewhere `$XDG_DOCUMENTS_DIR`). Comparison is case-insensitive on Windows.
4. Users create projects with a name, a folder or both (Projects > New project; without a folder `Store::create_project`), add a folder to a project by starting a session there (`LaunchSession.add_folder`, `Store::add_project_folder`: cwd or its git top level; a folder inside another project's folder here is a 409), remove this machine's folders (`Store::remove_project_folder`, `Change::DeleteProjectPath`; the project stays, also with none left), rename, and merge two projects (moves paths, sessions, records).

Projects without folders: a project with no `project_paths` row on any machine starts its sessions in `BLIRP_HOME/workspaces/<id>` on the machine that runs them (`Paths::ensure_workspace`, owner-only, created on demand by a launch or the files API). There is no path row for it: step 0 maps the folder, the workspace is per machine and never replicated as a folder (the hub's cloud sessions use the hub's own; its files can go through project file sync, §10a), and the project, its memory and its sessions replicate as usual. `ProjectSummary.workspace` names this machine's workspace for such projects. A project that has a folder anywhere uses its folders; launching it on a machine where it has none is refused as before (clone or pick a folder).

Chats: sessions that are part of no project live in a per-machine project flagged `chats` with the fixed id `chats-<machine id>` (`Chats (<machine name>)`; the local settings key `home_project_id` names it), created only by its machine. The flag replicates with the project row and is sticky (`write_row` keeps `MAX(chats)`), so every machine keeps chats out of project lists and merges all machines' buckets into one Chats group in the UI; Chats cannot be deleted, merged or merged into. blirp 0.1.0 filed these sessions in a Home project with a random id; at daemon start `Store::ensure_chats` creates the bucket and merges an untouched Home into it (like the cleanup: sessions and records move, the Home project is removed), while a Home with user-authored memory (renamed from `Home (<machine name>)`, a non-distiller brief version, a user or pinned record, a wiki page or a resource) or another machine's sessions stays a normal project. A bucket under another id (an earlier build, or this machine's id before `rebind_machine`) is merged into the canonical one the same way, unless it holds another machine's sessions or is `chats-<id>` of another known machine (a database copied from that machine); resolution only ever uses `chats-<machine id>`. Chats have no memory: nothing is injected into a chat (§9) and distilling one writes only the session summary. `Store::move_session` (`POST /api/sessions/:id/move`) re-points a session, its ingested subagents and the records it produced in its old project to another project, or to the Chats of the session's machine (409 when that machine has none yet; into Chats only unpinned distiller records move); replication allows another machine to re-point a session's project (§10). Local session writes keep the project stored at write time (`apply_in` re-reads it; only moves, merges and ingest re-files use `apply_move_in`), so a write built from a row read before a move never reverts it. Across machines a status write the owner made before it pulled a move can still land after the move at the hub; the owner's next write of the row carries the moved project again. Ingest files a new subagent session under its parent's current project (following merges; a parent in a removed project leaves it to the subagent's folder), and re-files a row filed under the home folder (§8) only while it is still in Chats and still in the project the plan saw inside the write transaction; a moved row keeps its project and only gets its folder corrected.

A merge records its target on the removed project (`projects.merged_into`, sticky, migration 10), so the workspace of a merged project (step 0) and `find_project_for_path` follow it to the surviving project.

Worktree sessions resolve to the parent repo's project (git common dir).

Cleanup of projects that are no actual project (`Store::retire_non_projects`, once per machine, settings key `projects.cleanup.chats`; 0.1.1 builds before Chats used `projects.cleanup.non_projects`, so the pass runs again with the current rules): run by the ingest engine at the start of a pass (never concurrently with one); on a node only after a pull reached the hub's head in this run (`Store::pulled_to_head`), so a change another machine made to such a project is seen first. `projects` has no provenance column. Projects the user makes (New project, with or without a folder; Add folder before it) start with `updated_at = created_at + 1`; resolution creates them with `updated_at = created_at`, which every later edit (rename, merge into, folder removal) changes. A project is untouched when it is no Chats project, still has `updated_at = created_at`, is named after one of its folders, has at least one session and all its sessions are this machine's `external` ones, all its folders are this machine's, none has a git remote (another machine may have joined it by that remote), it has no wiki pages or resources, and every record is an unpinned distiller record and every brief version a distiller one. It is eligible when each of its folders matches the step 3 scratch rules. blirp 0.1.0 created projects for Add folder with `updated_at = created_at` too, so untouched projects of plain folders (existing, no git work tree, no project marker at or above them) are only offered: `Store::chat_candidates` (`GET /api/projects/chat-candidates`, empty once the user dismissed it, local settings key `projects.chat_candidates.dismissed`) lists them for the Projects page, and `Store::move_project_to_chats` (`POST /api/projects/:id/to-chats`) moves the ones the user confirms, the same way, after checking that the project is still offered (409 otherwise): the folder checks run before the write transaction, which re-checks only that the project is still untouched with the same folders. A folder that is gone or unreachable (an unmounted drive) is never offered. Each eligible project is merged into this machine's Chats like a user merge, except that its folders and brief are not moved (they stay with the soft-deleted project): sessions, records and suggestions move. Everything goes through `apply` (the project delete, the moved rows), so the hub and other nodes converge. Another machine's scratch projects are cleaned by that machine. A local session write that would file a session under a deleted project it is not already in (resolved before the project was removed) fails with a conflict in `apply`, so its caller resolves again.

Implementation notes: a subfolder of an unregistered repo registers the repo top level (step 2). The Chats project has no `project_paths` rows (so it never captures subfolders by prefix). git runs as the `git` CLI with a timeout; when git is missing every folder is treated as non-git. Short-lived helpers (git, `--version` probes) run in their own process group / job: a timeout kills the whole tree, and after a normal exit output pipes that a background grandchild still holds are read for at most 1 s (the helper itself is left running). Blocking work (PATH scans, filesystem checks, shim parsing) never runs on the async runtime.

## 6. PTY supervisor (`blirp::pty`)

- `portable-pty` (vendored if needed for fixes). Windows: ConPTY. Ship `conpty.dll` + `OpenConsole.exe` next to the binary when available; fall back to the system ConPTY.
- Each live terminal: child process, master reader task, writer, `vt100::Parser` holding screen state (scrollback 10 000 lines), subscriber broadcast channel.
- Attach protocol (WS `/api/terminals/:id/ws`): server first sends a `snapshot` frame (formatted screen contents reproducing the current screen, including alt-screen state, cursor position and title), then streams raw output bytes. Client sends `input` (bytes), `resize {cols, rows}`. Multiple clients may attach; last resize wins.
- Framing (types `TerminalServerMessage` / `TerminalClientMessage` in `types.gen.ts`):
  - server -> client **text** frames are JSON: `{"type":"snapshot","cols","rows","data"}` (reset the terminal, then write `data`; it starts with `ESC c`, replays scrollback lines on the normal screen (all kept lines, at most the newest 16 MiB), redraws the screen and restores input modes, cursor and title; sent first and again whenever the client fell behind; relayed terminals accept frames up to 64 MiB for it), `{"type":"readonly"}` (right after the first snapshot when the client may not control the terminal: its input and resize frames are ignored), `{"type":"resize","cols","rows"}` (another client resized; never echoed to the client that asked), `{"type":"exit","status","exit_code"}` (process ended; the socket closes).
  - server -> client **binary** frames are raw PTY output bytes (may split UTF-8 sequences; feed them to the terminal as bytes).
  - client -> server **binary** frames are raw input bytes; **text** frames are JSON `{"type":"input","data":"..."}` or `{"type":"resize","cols":N,"rows":N}` (1-1000 each). Frames are capped at 1 MiB.
  - A live terminal that has exited is gone: attaching to a local session whose stored status is not live sends one `exit` frame (stored status and exit code) and closes with 1000, as a live terminal does when its process exits, so a client that raced the exit shows it instead of retrying; unknown ids (and a session still starting without a terminal) get 404 `terminal_not_found`. Use the session's status and events for its history.
  - Closing (this and `/api/events/ws`) always completes the WebSocket close handshake: a client's close is answered; the server closes with 1000 `exited` after the exit frame, 1001 `going away` when the daemon shuts down or the client's access changed (reconnect), and a relayed terminal passes the remote daemon's close code on (1011 when the remote side is unreachable).
- The daemon answers terminal queries itself when no client is attached (DSR cursor position `ESC[6n`, DSR status `ESC[5n`, primary DA `ESC[c`) so ConPTY and TUIs never block at startup. Attached clients (xterm.js) answer them instead; replies no client sent within 2 s (a client that is attached but gone, e.g. a laptop asleep before its relayed connection timed out, or one that never answers) are sent by the daemon.
- `CSI 3 J` (erase saved lines), which vt100 ignores, clears the kept scrollback (the screen state is rebuilt without it, normal screen only), as xterm.js does: TUIs that redraw their history after it (Claude Code) do not show it twice on reattach.
- Keep-awake (`sessions.keep_awake`, default on for the hub role, `blirp::keep_awake`): the status tick holds one OS sleep assertion while any terminal is live and releases it when none is: macOS `caffeinate -i -w <daemon pid>`, Windows `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` on a dedicated thread, Linux `systemd-inhibit --what=sleep --mode=block` around a loop that ends with the daemon. A helper that exits within 300 ms is a failed acquire carrying its stderr (systemd-inhibit's "Access denied" when polkit refuses a process outside a login session), never a held assertion; a failed acquire (or a helper that died later) is retried after 60 s. Reported as `keep_awake` in `GET /api/health`.
- Kill = terminate the whole process tree (Windows job object + ClosePseudoConsole; Unix: the tree is the child's process group plus every process of its session (the PTY child is a session leader; shells put background jobs such as `nohup x &` into groups of their own, and reparenting to init keeps the session) plus descendants still linked by parent pid, listed with `ps` and remembered at Stop time; it gets SIGHUP and SIGTERM, then SIGKILL after 3 s if anything is still alive, whether or not the leader already exited). The Windows job has `KILL_ON_JOB_CLOSE`, so sessions also end if the daemon dies; after a normal exit the rest of the tree is reaped the same way (like a terminal hangup). On Unix the output reader polls, so a process outside the group that keeps the PTY open cannot pin the reader thread: it gives up 1 s after the group is gone. The ConPTY is closed outside the PTY locks (the close waits for the reader, which needs the screen lock).
- Live terminals are registered per session id; a launch or resume reserves the id before spawning, so concurrent resumes of one session start one agent (the others get 409 `already_running`), and an exiting terminal records its exit and then removes only its own registry entry.
- Activity tracking: `last_output_at`; status heuristics in §7.
- Uploads (`blirp::uploads`, `POST /api/sessions/:id/uploads`): browsers paste only text into xterm.js, so the SPA intercepts a paste whose clipboard carries files or an image (unless it also carries real text: office apps add a picture of copied text, which is then pasted as text as before; text that only names the files, is empty, or is a single URL does not count) and files dropped onto the pane. Each file is sent as the raw request body (`?name=` the client's file name) to the daemon that runs the session, which needs `control` like terminal input, refuses a `Content-Length` over 25 MiB before reading and stops reading at 25 MiB (413 `file_too_large`), accepts only live terminals (404 `terminal_not_found`, checked again after the body is read), refuses a file that would take the session's folder past 500 MiB (413 `upload_quota_exceeded`), and writes a new file (`create_new`, never an overwrite; a counter on a same-millisecond clash) `uploads/<session>/<unix ms>-<name>`: the session id must pass `is_safe_id`, the name keeps only its last path component, letters, digits, `.`, `-`, `_` (other runs become one `_`), no leading or trailing dots, at most 120 bytes with its extension kept. Folders are 0700 and files 0600 on unix (Windows: profile ACL). The answer `UploadedFile {path, quoted, size}` has the absolute path and the form a terminal drop types on that machine (double quotes on Windows, backslash escapes elsewhere, unchanged when neither is needed). The SPA uploads files one at a time, skips dropped folders (with a notice), and pastes each `quoted` as its own (bracketed, when enabled) paste, separated and followed by a typed space, as native terminals do for dropped files (when the terminal socket is not open it shows the saved paths instead of dropping them); Claude Code and Codex attach an image whose path is pasted. `DELETE /api/sessions/:id` removes the session's folder; a task at start and then hourly deletes files older than 7 days and empty session folders (regular files directly in `uploads/<session>/` only, symlinks never followed). Uploads are files outside the database, so never replicated, and inside `BLIRP_HOME` outside `worktrees/`, so never ingested nor served by the project files API. A session on another machine is forwarded to it through the hub like its terminal (§10); proxied bodies are plain HTTP on the proxy stream, whose only size limit is this route's own.

## 7. Sessions and agents (`blirp::agents`)

An `AgentSpec` describes each agent: binary name(s), how to detect it on PATH, launch args, resume args, env injection, hook/MCP integration, transcript adapter. Custom agents are any command line from config (no memory ingest, but still tracked with status and injection via `BLIRP_MEMORY_FILE` env and AGENTS.md if the user enables it).

Launch (`POST /api/sessions`): body `{project_id | cwd, agent, prompt?, worktree?: bool, continue_from?: session_id, machine?: id}` (`cwd` must be absolute, else 400):
1. Resolve project + cwd. If `worktree` and project is git: `git worktree add ~/.blirp/worktrees/<project>/<name> -b blirp/<name>`; name is `adjective-animal-xxxx`. If the session row then cannot be written, the worktree is removed again (the branch is kept).
2. Create session row (`starting`, origin `blirp`).
3. Render memory injection (§9) to `~/.blirp/launch/<id>/memory.md`.
4. Build argv/env per agent:
   - claude: `claude --session-id <new uuid> --settings <launch/settings.json> --mcp-config <launch/mcp.json>` (settings contains blirp hooks for SessionStart, UserPromptSubmit, Stop, Notification, SessionEnd, PreCompact). Store the uuid as `agent_session_id` immediately.
   - codex: `codex -c developer_instructions=<user's own developer_instructions + memory> -c mcp_servers.blirp.command=... -c mcp_servers.blirp.args=["mcp"] -c mcp_servers.blirp.env={...}` placed before any `resume` subcommand. Codex 0.153 has SessionStart hooks, but non-managed hooks only run after the user trusts their exact definition, so launch-time context uses `developer_instructions` (verified with `codex debug prompt-input`).
   - opencode, pi, gemini, cursor, amp, aider, dsh: per §9 table.
   - Windows npm `.cmd` shims (`codex.cmd`, `gemini.cmd`, ...) that run node (`SET "_prog=node"`, or the older `"%~dp0
ode.exe"` form) are unwrapped to `node <script>` so arguments never pass through `cmd.exe`. Other `.cmd/.bat` files run as `cmd /d /v:off /c %BLIRP_CMD_LINE%`, with the escaped command line in the `BLIRP_CMD_LINE` env var (the PTY spawner cannot pass a raw command line): the script path is quoted, every argument with anything but word characters is quoted with embedded quotes doubled (so `& | < > ^ ( )` stay literal), and cmd expands the variable once, so `%` in arguments is never expanded. Arguments with line breaks are rejected (400).
   - Launch integration failures (render, file writes) are logged and the agent starts without memory.
   - Env always: `BLIRP_SESSION_ID`, `BLIRP_PROJECT_ID`, `BLIRP_HOME`, `BLIRP_MEMORY_FILE`, plus `TERM=xterm-256color`, `COLORTERM=truecolor`. Parent-agent markers (`CLAUDECODE`, `CLAUDE_CODE_*` session/child/messaging vars, `CLAUDE_PID`, `CLAUDE_EFFORT`, `CODEX_SANDBOX`) are removed so a daemon started from inside an agent does not leak them.
   - claude login token: a daemon that cannot reach the macOS login keychain (a LaunchAgent on a locked Mac, a start over SSH) sees claude as logged out, and claude may hang before its prompt. `blirp agents set-token claude` (token on stdin, hidden on a terminal; trimmed; refused when empty, over 4096 chars or with whitespace/control chars inside) or `PUT /api/agents/claude/token` (admin) stores a `claude setup-token` token in `BLIRP_HOME/secrets/claude_oauth_token` (`blirp_core::claude_token`: dir 0700, file written 0600 to a fresh temp file and renamed; Windows: profile ACL); `clear-token` / `DELETE` removes it. It is read at every spawn and passed as `CLAUDE_CODE_OAUTH_TOKEN` (the variable the Claude Code authentication docs name for `setup-token` tokens) to claude only: PTY sessions, the claude summarizer and the `claude auth status` probe; never when the daemon's own environment sets that variable (it is inherited and wins), unless that value equals the stored token: then it is a copy inherited from a claude session blirp launched (`blirp daemon --detach` run by claude), which every CLI invocation removes from its own environment before any thread starts, so neither the daemon nor anything it starts inherits it. The file is written to a temp file with a random name (`create_new`, 0600) and renamed; `clear` also removes leftover `claude_oauth_token.*.tmp`. `GET /api/agents` re-detects when the token file's status, mtime or size changed. The token is never logged (`SpawnRequest`'s Debug omits env values), never in the database (so never replicated) and never returned by the API: `AgentInfo.token` is `{stored, env}` for claude, null for other agents.
   - shell: `$SHELL` (unix, else `/bin/sh`); Windows `pwsh`, else `powershell`, else `%ComSpec%`.
   - Binaries resolve on PATH; on Windows only `.exe/.com/.cmd/.bat/.ps1` count (npm's extensionless shims are skipped), `.cmd/.bat` run through `cmd` as above, `.ps1` via PowerShell `-File`. The same wrapping applies to `--version` probes, summarizer runs and `open` in an editor shim.
   - Resume (`POST /api/sessions/:id/resume`, same session row) with `agent_session_id`: claude `--resume <id>`, codex `resume <id>`, opencode `--session <id>`, gemini `--resume <id>`, cursor `--resume <id>`, amp `threads continue <id>`; pi, aider, dsh, shell and custom agents (or no known id) relaunch fresh in the session folder.
5. Spawn PTY; if `prompt` given, type it after the agent is ready (first output idle for 1.5 s, at most 60 s) followed by Enter. The prompt is sent as a bracketed paste when the application enabled bracketed paste mode. While any interactive dialog is on screen the prompt waits for the user to answer it (up to 10 min, then it is dropped): a selection menu with a highlighted numbered choice (claude `❯ 1.`, codex `› 1.`, also inside a box), "Enter to confirm" / "Esc to cancel" hints, `(y/n)` questions, and trust, permission ("Do you want to ...") and "New MCP server" wording. Typing into a dialog would answer it (a digit picks a choice, Enter confirms the default, e.g. approving an MCP server from the user's `.mcp.json`); blirp never answers dialogs. The screen is checked again before Enter is sent. Fixtures of captured screens live in `crates/blirp/tests/fixtures/screens/`.

Status:
- From hooks when available (claude: UserPromptSubmit -> working, Stop -> idle, Notification(permission/idle prompt) -> waiting, SessionEnd -> completed).
- Else heuristics: output within the last 2 s -> working; otherwise idle.
- Process exit: code 0 -> completed, else failed. A user Stop is recorded as intent: `completed` with `exit_code` null and `stopped_by_user = true` (the kill's own code, e.g. 1 from TerminateJobObject, is dropped), so the UI shows "Stopped"; the terminal `exit` frame has `exit_code: null` too. Resume clears the flag. Daemon shutdown ends running sessions as `detached`.
- Heuristics never overwrite `waiting` (hook-owned) or a final status.
- On daemon restart, blirp-launched sessions whose process is gone become `detached` (ingested external sessions keep their status); UI offers Resume (agent resume flag with `agent_session_id`).

Continue in / fork: `continue_from` builds a handoff pack (§9) from the source session and passes it as the initial context of a new session with any agent; `parent_session_id` records lineage. Without `project_id`/`cwd` the new session starts in the source session's folder (or its project when that folder is not on this machine). Before the pack is built, a source of this machine whose transcript moved past its last summary is distilled (bounded wait, never fails the launch; §9 Handoff pack). Fork is `continue_from` with the same agent.

## 8. Ingest (`blirp::ingest`)

One adapter module per agent implementing:

```rust
trait Adapter {
    fn id(&self) -> &'static str;
    fn roots(&self) -> Vec<PathBuf>;                        // dirs to watch, per OS, honoring env overrides
    fn scan(&self, store: &Store) -> Result<Vec<Source>>;   // discover transcript sources
    fn ingest(&self, src: &Source, cursor: Option<Cursor>, sink: &mut dyn EventSink) -> Result<Cursor>;
}
```

- Watch roots with `notify` (debounced 500 ms) plus a full rescan every 5 min and at startup. Hooks that report a `transcript_path` hand it over through `IngestTrigger` (§9 Hooks); hints are collected for 250 ms from the first one and then join the next pass like a watcher event (a path outside every adapter root is ignored; on Windows roots and known sources are matched case-insensitively after removing a `\\?\` prefix, and a hinted file continues the known source under its scanned spelling), so hooked sessions are ingested within about a second even when their root is not watched. Only roots that exist are watched; the rescan adds roots created later (agent installed after blirp). A watcher event re-reads just the changed known file; anything else (new file, database) rescans that adapter.
- Passes run on the blocking pool, one at a time (adapters of a pass in parallel, sources of one adapter sequentially, most recently modified first), never on the async runtime or the PTY path. Events are written in `Store::ingest_tx` transactions of at most 1000 events with `apply` semantics (row + outbox); a source's cursor is stored in the transaction of its last batch. Shutdown stops a pass between events.
- Incremental: a `Source` carries a fingerprint (size + mtime for files, `time_updated` for database rows); an equal fingerprint in the stored cursor skips the source. JSONL cursors store byte offset + line count guarded by file identity (creation time / inode) and a hash of the first 256 bytes; only complete lines are consumed (a final line without newline counts once the file has been quiet for 60 s). SQLite stores keep the last consumed `(time_created, id)`; JSON files the message count (amp also keeps a seq base: when a thread was edited shorter, the base moves past every index used so far, so later messages never reuse an old message's seqs). Truncation, rotation or a changed head -> re-read from 0, dedupe on `(session_id, seq)` (so a file rewritten with *different* content at the same positions is not re-imported; agents append, so this only affects hand-edited files).
- Seqs are deterministic for the same source content and increase with arrival (the distiller consumes events past `distilled_through_seq`): line-oriented sources use `line_index * 1024 + n`; sources without stable lines (gemini, cursor `store.db`, opencode) keep a counter in the cursor and dedupe by message / tool-call id; cursor `store.db` blobs are content addressed (identical messages share a blob), so its messages are deduped by their position in the tree (a count of stored messages in depth-first order), never by blob id.
- Handles compressed Codex rollouts (`.jsonl.zst`) and dsh logs (`.jsonl.zstd`) via `zstd` (appended frames are read incrementally; a torn last frame waits).
- Claude user lines the harness wrote (`isMeta`, an `origin.kind` other than `human` such as `task-notification`, `coordinator`, `peer`, `auto-continuation`, and text starting with `<task-notification>`, `<system-reminder>`, `<local-command-*>`) are `system` events, not the user's prompts: they neither show as the user's words nor make a session due for distill.
- Normalizes into `sessions` + `events`. `text` is human-readable and redacted (`blirp_core::redact`, applied to text, titles and meta); tool calls are `tool(args preview)` in text with full (redacted) args in `meta_json`; tool results are cut to 4 KiB of text, other text to 64 KiB; `meta_json` is capped at 16 KiB. Edit/write tool calls (and `apply_patch` payloads) add one `file_edit` event per path (`meta.path`). Compaction summaries are `summary` events; injected context (Codex `<environment_context>`, Claude local-command output) is `system`. Reasoning/thinking is not stored.
- Scripted runs: a transcript that records a headless run, no interactive one and at most one prompt creates no session and no project (`ingest::Launches`, kept in the adapter's cursor state and reported to the sink before the run's events can be flushed). Headless: claude `entrypoint` `sdk-cli`/`sdk-ts`/`sdk-py` (`claude -p`, the Agent SDKs); codex `session_meta.source` `exec`. Interactive: any other claude `entrypoint`, and a claude user or assistant line without one (older Claude Code); any other codex `source`. Prompts: claude user turns counted by `promptId` over lines the user wrote (not tool results, `isMeta`, `isCompactSummary`, an `origin.kind` other than `human`, or harness text), codex `turn_context` lines (a resumed codex session may continue its rollout without a new `session_meta`), not counting what a codex fork copied from its parent (its parent's `session_meta` and history). So an app someone chats in over the Agent SDK (Zed, Conductor, ...), a scripted run resumed interactively and an interactive session continued with `claude -p --resume` are sessions; when a transcript stops looking scripted it is read again from the start (its cursor is reset once). A blirp-launched row that links to it keeps it. A claude subagent transcript (it inherits the parent's entrypoint and has one prompt) is scripted only when its parent's transcript is and no stored session is its parent; when a session transcript is read for the first time or stops looking scripted, the cursors of its subagent transcripts still marked headless are dropped (`Store::delete_cursor`), so the next full pass reads them from the start and a subagent written only during the first prompt is stored too. A row a hook created for it (`origin = external`, no events yet) is removed when the transcript is read, with the project the hook resolved when it holds nothing else (`Store::remove_headless_sessions`). Sources read before this rule count as interactive; instead, on first start after upgrading, a one-time cleanup (settings key `ingest.cleanup.headless`, at the start of an ingest pass; on a node once a pull reached the hub's head) reads the whole transcript of every ingested `external` claude and codex session of this machine that is no subagent (subagents go with a removed parent and stay with a kept one) and removes the scripted ones like a user delete (`DeleteSession` with its ingested subagents, replicated), together with the records the distiller made from them (`updated_by = distiller`, unpinned; kept, with the source cleared, when a remaining session of the project was distilled after the record was created, since the distiller adds no second record with an active record's title and that session may have reached it too) and the projects that held nothing else and show no sign of the user (the untouched rule of §5), and drops their ingest cursors so a transcript that grows later is judged from its start. A row whose transcript is gone or unreadable is kept; brief versions, resolutions and suggestions are left as they are.
- Sessions: `project_id` from `resolve_project` on the transcript's cwd, the folder the session started in, with the rules for sessions blirp did not start of §5 steps 0 and 3 (`IngestEnv::non_projects`, which maps `BLIRP_HOME/workspaces`) (`resolve_project_lenient` when the folder no longer exists: the path is normalized (no `\\?\` prefix, trailing or doubled separators, `.` and `..` resolved lexically; matched case-insensitively on Windows), then prefix match, else the project of a folder with the transcript's git remote (codex `session_meta.git.repository_url`; this machine's first), else Chats (a gone folder cannot show it was a project); no cwd -> Chats). The cwd decides the project, the launch link and the BLIRP_HOME exclusion, so a session row is never created before it is known: adapters report session facts as soon as they read the cwd (`report_cwd`), and a mid-read flush keeps a new session's events buffered until then (or until the end of the read, when an unknown cwd means Chats). A row that was nevertheless filed under the home folder is re-filed (cwd and project) by a later read that covers the transcript from its start; on first start after upgrading, the cursors of such rows are reset once (settings key `ingest.repair.home_filed`) so their transcripts are re-read, and one that turns out to be inside BLIRP_HOME is deleted. Title: the agent's own title (Claude `ai-title`, opencode/pi/amp/cursor names, Gemini summary, dsh title), else the first user prompt (first line, 80 chars); set only while the title is empty, so a distiller or user title is never overwritten. Tokens and cost are absolute totals: the transcript's own cost when it has one (Claude `cost-state`, opencode, pi, aider), else an estimate from the dated static price table in `ingest/pricing.rs` (unknown models cost 0). `compacted_at` is the time of the newest compaction summary read (a `summary` event: Claude `isCompactSummary`, codex `compacted` lines, opencode summary messages, pi `compaction`; not pi `branch_summary`, stored with meta `branch_summary: true`); it only grows, rows ingested before migration 16 get it at their next compaction, `context_near_full_at` is the time a codex `token_count` event's latest call input (`last_token_usage.input_tokens`) crossed 90% of its `model_context_window` (set on the crossing, not while it stays above; the state is kept in the cursor). The web UI offers a fresh session from a running session once per new value of either (the later one counts; per browser dismissal). No context-window sizes are assumed: only agents that report one (codex) get the second signal. `started_at` / `last_activity_at` come from event timestamps (or the store's own update time); external sessions are `working` while their source changed in the last 2 min, else `completed` with `ended_at = last_activity_at`; a 30 s sweep completes external sessions that went quiet.
- Subagents are child sessions with `parent_session_id` set: Claude `<sessionId>/subagents/agent-<id>.jsonl` (`agent_session_id = "<sessionId>:agent-<id>"`, title from its `.meta.json`), opencode `session.parent_id`, Gemini `chats/<parentId>/`, Cursor `subagents/`, Codex Desktop rollouts with `thread_source: "subagent"` (`parent_thread_id`; a forked one's copy of the parent's history, lines before `subagent_history_start_ordinal`, is skipped, see agent-formats.md). A subagent ingested before its parent is linked on a later read of it (the parent id is kept in its cursor). One-time repair of what earlier builds stored (settings key `ingest.repair.codex_subagents`, at ingest start, counts logged; retried at the next start if it fails): for each Codex subagent rollout of a session of this machine, its cursor is reset unless it is linked (the re-read links the parent); a fork whose file confirms the copy line by line (every line below `subagent_history_start_ordinal` has `ordinal` = its line index, the second is the parent's `session_meta`) loses its events below `start * 1024` through a replicated `Change::TruncateEvents` (§10); a fork title equal to the parent's (taken from the copied first prompt) becomes the subagent title; and unpinned records only the distiller wrote from forks are deleted (replicated), unless another session of the project was distilled after the record was created (that run had it as context; the rule of the scripted-run cleanup above, one helper). Forks whose copy is not confirmed are left as they are (logged). Claude tool output spilled to `tool-results/*.txt` is linked by path in the result's `meta.result_file` with at most a 4 KiB preview.
- Links to blirp-launched sessions: by `agent_session_id` (claude, set at launch), else by (agent, same folder, first event within 60 s after launch, closest launch wins) on this machine; linking sets `agent_session_id`. Ingest only ever writes sessions of this machine: a transcript whose `agent_session_id` (or whose parent's) already belongs to a session replicated from another machine (e.g. a synced agent config dir) is skipped with a warning, because that machine ingests it and owns the row. A linked or blirp-owned row keeps its `origin`, `status`, `started_at` / `ended_at`, `worktree` and `cwd`; ingest only fills the title (if empty), tokens, cost, transcript path, branch and last activity.
- Sessions started outside blirp are ingested as origin `external`; the daemon's restart handling (`detached`) applies to blirp-launched sessions only.
- Transcripts whose cwd is inside `BLIRP_HOME` (except `worktrees/` and `workspaces/`, which hold the user's work) are blirp's own background runs (the distiller's scratch dirs, `BLIRP_HOME/distill/`) and are skipped.
- Retention: history is permanent. A source file or database row that disappears never deletes blirp rows.
- Server events: `session_created`, `session_updated` (at most one per session per second; a suppressed update is sent once its second has passed) and `project_updated` for projects created by resolution.
- `blirp doctor` prints how claude logs in (token from the environment, stored token, or keychain / credentials file, plus `claude auth status`; from the running daemon's `/api/agents`, else this shell) and one line per adapter: root found, source count, last ingest time (settings keys `ingest.<adapter>.last_at` and `.sources`).
- Each adapter ships fixture transcripts under `crates/blirp/tests/fixtures/<agent>/` and a test asserting the normalized output (`crates/blirp/tests/ingest.rs`).

## 9. Memory (`blirp::memory`)

### Redaction (`blirp-core::redact`)
Applied to every event text and meta before storage, sync or summarization, and to memory written on this machine: `Store::apply` redacts record titles/bodies, brief bodies, wiki titles/bodies and resource titles/URLs/meta before writing and queueing them (UI, API, MCP `mem_record`, accepted suggestions, distiller). Rule set: gitleaks-compatible regexes compiled once (AWS, GCP, Azure, GitHub, GitLab, Slack, Stripe, OpenAI, Anthropic, generic `api_key|secret|token|password` assignments with high-entropy values, private key blocks, JWTs, connection strings with credentials, `.env`-style lines). Replacement `[REDACTED:<kind>]`. Unit tests for every rule with positive and negative cases.

### Distill
Trigger: a session quiet for `memory.distill_idle_secs` (default 300) in status `idle`, `completed`, `failed` or `detached`, with new `user` or `assistant` events past `distilled_through_seq` (tool calls and results, system events and compaction summaries alone do not count), or a session that ended (process exit and the `SessionEnd` hook enqueue a job that starts 10 s later, so the transcript's last lines are ingested first and both make one job; a scheduler scans every 30 s). The scheduler applies the quiet time to ended sessions too: an external session is marked `completed` after 2 quiet minutes (§8) and `working` again by its next transcript write, so a long-running external session would otherwise be distilled at every short pause. An automatic job with no new `user` or `assistant` event past `distilled_through_seq` is dropped before it takes budget. Only sessions active in the last 7 days are auto-distilled, so freshly ingested old history does not eat the budget. Only this machine's sessions are distilled: a replicated session is distilled on its origin machine and its summary and records arrive by sync (manual distill answers 409 `remote_session`). Ingested subagent children (origin `external` with `parent_session_id`, §8) are not auto-distilled, also when queued by a hook or exit: the parent's transcript already carries the subagent's task (tool call) and final report (tool result), so the parent's summary covers them without spending budget; a manual distill still runs. `continue_from` sessions (origin `blirp`) are distilled normally. The check runs before a job takes budget. One job at a time (in-process queue, deduplicated per session; the worker takes the first priority job (a handoff waits for it, §9 Handoff pack), else the first job whose start time has passed, so a delayed job never holds up ready ones); daily budget `memory.daily_distill_limit` (default 40 jobs, counted per UTC day in the `settings` key `memory.distill_budget`; manual `POST /api/sessions/:id/distill` counts too and answers 409 `nothing_to_distill` when the session has no events).

Summarizer backends (config `memory.summarizer`, default `auto`), all with a 180 s timeout that kills the whole process tree:
- `claude`: `claude -p --model sonnet --output-format json --safe-mode --strict-mcp-config --no-session-persistence --tools ""`, prompt on stdin, with the stored login token (§7). `--safe-mode` disables hooks, plugins, CLAUDE.md and MCP; `--no-session-persistence` keeps the run out of `~/.claude/projects` (so ingest never sees it); `--tools ""` removes all tools. Reply: the `result` field of the JSON envelope (`is_error` -> failure).
- `codex` (picked by `auto` only as the default agent): `codex exec --json --ephemeral --skip-git-repo-check --ignore-user-config --sandbox read-only -c web_search="disabled" --disable <f>... --output-last-message <tmp>` with `hooks`, `shell_tool`, `unified_exec`, `view_image`, `apps`, `plugins`, `browser_use`, `computer_use`, `multi_agent`, `image_generation`, `sleep_tool`, `goals`, `tool_suggest`, `skill_search`, `code_mode_host` disabled (a codex that does not know one of these names refuses to run: "Unknown feature flag", classified as unavailable, so distilling pauses). `--ignore-user-config` keeps the user's `config.toml` out (its MCP servers, plugins, hooks, model and provider; `-c mcp_servers={}` does not remove configured servers); web search is on by default. Verified against codex 0.153.2 by capturing the request it sends: no tools at all (without these two flags it sent the user's MCP servers and `web_search`). Codex has no single "no tools" switch, so a newer codex can add a built-in tool these flags do not cover; that is why `auto` uses it only when the user made it the agent for new sessions (they already run it with every tool on in these projects; the residual risk is a transcript steering an uncovered tool inside the read-only sandbox and empty scratch dir). Prompt on stdin; the reply is the last-message file, else the last `item.completed` `agent_message` of the JSONL stream (`error`/`turn.failed` events are reported).
- `ollama`: `POST $OLLAMA_HOST|http://127.0.0.1:11434/api/chat` with `format: "json"`, `stream: false`, model `memory.ollama_model`.
- `none`: never distill.

Summarizer failures are classified. A failure of the summarizer itself (auth: "not logged in", invalid key; unavailable: not installed, not reachable; rate or usage limits, including Claude Code's "You've hit your session limit" and "weekly limit", also when `claude -p` returns them as a plain result) pauses automatic distilling with a circuit breaker: the unit of budget is given back, the session records no failure (it stays eligible), and automatic jobs are skipped quietly until the pause ends (5 min, doubling on each failed retry up to 6 h; the first job after it is the probe). Success resumes distilling. Pause changes are logged once per attempt; "budget used up" once per day. `GET /api/settings` reports `distill {paused, reason, retry_at, budget_used, budget_limit}`. Manual distills always try. Other failures (timeouts, invalid output) fail only that session as below.

`auto` (`distill::pick_auto`, resolved at every run): the backend of `agents.default` when that is `claude` or `codex`, on PATH and not reported logged out (`claude auth status` with the stored token, `codex login status` exit 1 "Not logged in"; unknown counts as logged in), and for codex at least `CODEX_MIN_VERSION` 0.153.0 by `codex --version` (older or unknown: never picked, the feature names above would be refused); else claude on PATH and not logged out; else ollama answering `/api/tags`; else an installed but logged-out CLI (the default agent's first), whose run fails with its sign-in error and pauses distilling (Auth). Probes run only when needed (claude's not when the default codex is ready, ollama's not when a CLI is). `GET /api/settings/summarizer` returns `SummarizerPick {backend, model, default_agent, fallback: null|no_backend|not_installed|not_logged_in|outdated}` for Settings > Memory (its own route: the probes take about a second; cached 30 s in `Distiller`, keyed on `agents.default`, `memory.ollama_model` and the claude token file stamp). Every summarizer runs in a fresh empty dir `BLIRP_HOME/distill/run-*` (removed afterwards; inside BLIRP_HOME and outside `worktrees/`, which is exactly what ingest skips, so even a summarizer that persists its session is never ingested and distilled in turn) with `BLIRP_DISTILLING=1` (blirp hooks exit immediately when set) and without `BLIRP_SESSION_ID`/`CLAUDECODE`-style env.

Input: redacted, compacted transcript of the events past `distilled_through_seq` (all events when nothing is new, e.g. a manual re-run) (user prompts verbatim; assistant text; tool calls as one-line `TOOL: ...` (<= 300 chars); tool results `RESULT: ...` (<= 400 chars); file edits and system lines one-line), capped at `memory.distill_max_chars` (default 60 000, keep head 20% + tail 80% around a `[... N characters omitted ...]` marker), plus the current brief and active records (with ids) of the project, and, when continuing, the session's previous summary and items as context (the model returns title and summary for the whole session and only new or changed items). Events are selected in SQL (`Store::distill_events`): the first events filling 20% and the last filling 80% of the budget by an estimate that mirrors the line caps; the ones in between are never loaded and appear as `[... N events omitted ...]`.

Output (JSON, validated: required keys, types and no duplicate keys; keys outside the contract are ignored; one retry with the validation error on invalid output, then the attempt fails):
```json
{ "title": "short session title",
  "summary": "3-6 sentences",
  "decisions": [{"title": "...", "body": "..."}],
  "open_threads": [{"title": "...", "body": "..."}],
  "resolved_record_ids": ["..."],
  "gotchas": [{"title": "...", "body": "..."}],
  "files": ["relative/paths"],
  "brief_md": "full replacement brief, <= 1500 tokens" }
```
Validation: title and summary non-empty (title <= 200 chars), item titles non-empty, <= 20 items per list, unknown record ids dropped, `brief_md` <= 12 000 chars (`""` = no change). Every string of the reply is then redacted. The JSON object may be wrapped in prose or code fences. Backend failures (process error, timeout, auth) are not retried.

Apply (`Store::apply_distill`, one transaction): session title (if unset) + `summary_json` (`SessionSummary`: title, summary, decisions, open_threads, gotchas, resolved_record_ids, files, backend, distilled_at, through_seq, error; a continued run keeps the earlier items, a new item replaces an earlier one with the same normalized title, files and resolved ids are merged) + `distilled_through_seq`; records: an item whose kind and normalized title (lowercase words, punctuation ignored) match a record this session produced earlier (any status) updates that record's title and body (never a user-edited one); otherwise a new record (`updated_by = distiller`, `source_session_id` set), skipped when an active record of the same kind and normalized title exists; resolve records; brief: if `memory.brief_mode = auto` (default) write a new version (history kept, user can revert); if `review`, create a `suggestion` instead. The plan carries the brief version the summarizer was shown: if the brief changed during the run (a user edit), the result becomes a suggestion in either mode and the edit stays. Records edited by the user (`updated_by = user`) are never modified by the distiller; resolving one creates a record suggestion. A failed attempt keeps any earlier summary and sets `summary_json.error = {message, at, through_seq}`; the session is retried only after newer events arrive (or on a manual distill).

`render_injection(project, exclude_session?) -> String` (markdown, hard cap `memory.inject_max_chars`, default 8000):

<brief, at most half the budget; "_No project brief yet._" when empty>
## Pinned            (active pinned records of any kind, notes and plans included, labelled `[kind]`, max 8)

A Chats project renders nothing (chats share no memory). The MCP tools and `blirp mem` keep working on demand.

### Hooks (`blirp hook <agent> <event> [--global]`)
Reads the agent's hook JSON from stdin (at most 400 ms), exits immediately when `BLIRP_DISTILLING=1`, POSTs `{blirp_session_id, cwd, global, payload}` to `/api/hooks/:agent/:event` using runtime.json (at most 1.5 s, and never past 1.8 s - 300 ms counted from process start, so the offline fallback can still print), prints the agent-specific output and always exits 0; a watchdog ends the process at 1.8 s after start. Output: claude/codex/gemini SessionStart `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":...}}`; gemini other events `{}`; cursor `sessionStart` `{"additional_context":...}`, `beforeSubmitPrompt` `{"continue":true}`, others `{}`. When the daemon is down, SessionStart falls back to `launch/<BLIRP_SESSION_ID>/memory.md`, else renders from the database opened read-only for the payload's folder.

Daemon side: events are normalized (claude/codex `UserPromptSubmit`, gemini `BeforeAgent`/`AfterAgent`/`PreCompress`, cursor camelCase names). The session is found by `BLIRP_SESSION_ID`, else `(agent, agent_session_id)`; a session of another machine is left alone (empty reply: no status change, injection or distill); unknown sessions with an id and a folder become new `external` sessions (project resolved from the folder with the scratch-folder rules, §5), except scripted runs (§8): the hook client sets `headless` when the agent is claude and `CLAUDE_CODE_ENTRYPOINT` starts with `sdk-`, and the daemon also refuses a transcript whose ingest cursor already says headless (`ingest::known_headless`); a session found by id keeps getting updates either way. Such a SessionStart still returns the memory of the project that contains its folder, found read-only (`find_project_for_path`: nothing is created), because an app someone chats in over the Agent SDK looks the same to a hook; ingest decides from the transcript whether it becomes a session (§8). Hooks link `agent_session_id` and `transcript_path` and hand the transcript path to the ingest subsystem (`IngestTrigger::transcript_hint`; the daemon installs the ingest service's trigger, a no-op when ingest is disabled). Status: PromptSubmit -> working, Stop -> idle, Notification -> waiting, SessionEnd -> completed (not for `reason = clear`, and not while blirp still owns a live PTY; the exit sets the final status), SessionStart makes a resumed external session live again. SessionEnd enqueues a distill. SessionStart returns the launch `memory.md` on a blirp session's first start (it may carry a handoff pack), else a fresh render. A `--global` entry firing inside a blirp launch that has its own hooks (claude, gemini) is ignored; for codex it updates status but injects nothing (developer instructions already did).

### Agent Skills (`blirp skills install|uninstall|list [--agent X] [--project DIR] [--force]`)
Opt-in, separate from global integration, CLI only. `skills/<name>/SKILL.md` (Agent Skills format: YAML frontmatter `name` = folder name, lowercase-hyphen, <= 64 chars, and `description` <= 1024 chars) are embedded with `include_str!` and written to `$CLAUDE_CONFIG_DIR|~/.claude/skills` (claude; amp always `~/.claude/skills`; opencode and cursor read it too) and `~/.agents/skills` (codex, gemini, opencode, cursor, pi), or `<DIR>/.claude/skills` and `<DIR>/.agents/skills` with `--project`. Each skill folder gets `.blirp-skill` = `sha256:<hex>` of the SKILL.md blirp wrote: a folder with a matching hash is blirp's and unedited (`installed`, or `outdated` when this binary's text differs, then refreshed by install); a SKILL.md byte-identical to this version's counts as blirp's whatever the marker says (install rewrites the marker), so an interrupted install is not taken for an edit; a mismatch is `modified`, no marker `not_ours`; neither is overwritten without `--force` (old file copied to `SKILL.md.blirp-backup`, `.1`, ... unless an identical backup exists) or ever removed; symlinked folders are skipped. Writes are temp + rename. `uninstall` scans the folder, so skills a later version dropped are removed too; `blirp uninstall` runs it for the home folders; after a successful `blirp update` the new binary runs `blirp skills refresh` (rewrite `outdated` skills in the home folders only; its failure is printed, never fails the update); `blirp doctor` reports per folder. A unit test parses every `blirp ...` line in the skills with the clap definition. Skills only instruct the agent to run the CLI (read-only commands freely, anything that changes or removes state after the user agrees); the MCP server gets no admin tools.

### Handoff pack (continue in / fork)
Fresh summary first (`memory::handoff`): when the source has new `user` or `assistant` events past `distilled_through_seq` (the distill trigger's rule, `Store::has_new_content`), the launch distills it before building the pack, waiting at most 90 s (`REFRESH_WAIT`, below the summarizer's own 180 s timeout). The run is a priority job of the normal queue (`Distiller::enqueue_priority`): it runs next (a queued job of that session is moved up instead of doubled, keeping its start time, so a session that just ended still waits out its 10 s for the last lines while nothing else starts; a running one is waited for), one run at a time, counted against the daily budget, and under the automatic rules (not `manual`): nothing is started when the summarizer is `none`, paused by the breaker, the budget is used up, or the source is an ingested subagent (covered by its parent); a job left over after a timeout follows the same rules. Another machine's session (a paired machine's, or a cloud session run by the hub) is never distilled here: its owner distills it and the pack uses the summary synced from there. In each of those cases, and on a timeout (the run continues and lands on the source session) or a failed run, the launch still goes ahead with the last summary and the header says why it was not refreshed (`_The summary was not refreshed for this handoff (<reason>); the last turns below are current._`).

The refresh runs before anything is made for the new session (the worktree), and the launch handler runs as its own task, so a client that goes away meanwhile (closed tab, dropped forward) neither cancels a launch halfway nor leaves a worktree behind. One handoff per source at a time on a machine (`AppState::handoffs`): a second one while the first is prepared answers 409 `handoff_in_progress` (later ones are fine). A daemon shutting down during the refresh answers 503 `shutting_down` and starts nothing. A launch forwarded to another machine (`machine`) with a source of this machine refreshes the summary here first (only the owner distills), answers 503 `shutting_down` if the daemon stops meanwhile, and, when a new summary was written, waits up to 10 s (`PUBLISH_WAIT`, best effort) until this machine's outbox reached the hub, so the target can render the pack from it. A target other than the hub must still pull it, which is not waited for; if it has not, its pack notes the older summary. The launch request answers after all this; the web UI shows "Summarizing session..." on the source while it waits and a notice for `handoff_in_progress`.

Header (source title, agent, date, folder) + the source session's summary + the project brief + its last N (default 12) user/assistant turns (each <= 1 500 chars) + files touched (distilled `files` plus `file_edit` events) + open threads, capped at 12 000 chars (oldest turns are dropped first, then the brief is cut). It is appended to the new session's injected memory (`memory.md`) and saved as `launch/<id>/handoff.md`; the initial prompt (unless the request gives one) is "Continue the work described in the blirp handoff above.", or for agents without injection "Read the blirp handoff in <handoff.md> and continue the work described there." (none for `shell`).

### MCP server (`blirp mcp`, stdio; also Streamable HTTP at `/mcp` on the daemon)
Built with the official Rust SDK `rmcp` (3.4). Tools (replies are plain text written for models):
- `mem_search {query, project?: "current"|"all"|id, kinds?: ["record"|"event"], limit?}` -> ranked hits (records and transcript events) with session id, seq, date, agent and snippet (matches in `**bold**`).
- `mem_session {session_id, from_seq?, limit?}` -> session header, summary, files and a page of events (`from_seq` pagination hint).
- `mem_recent {project?, limit?}` -> recent sessions with summaries.
- `mem_brief {project?}` -> current brief + all active records grouped by kind.
- `mem_record {kind, title, body}` -> create a record in the current project (stdio: via the daemon API; errors clearly when the daemon is down).
Current project = `BLIRP_PROJECT_ID` env, else the registered project containing the server's working directory (read-only lookup, nothing is registered), else (HTTP) the `?project=` query parameter of the `/mcp` URL. stdio opens the database read-only. `/mcp` sits behind the normal bearer/cookie auth and only accepts loopback `Host` headers.

## 10. Sync (`blirp-sync`)

Roles: `standalone` (default), `hub`, `node`. Transport: iroh 1.x (QUIC, NAT traversal, relay fallback). `sync.relay`: `default` = n0 relays plus n0 DNS address publishing/lookup (peers are found by id alone), `disabled` = direct addresses only, `<url>` = that relay only. Local-network discovery (mDNS, service `blirp`) is on unless `sync.lan_discovery = false` (then a join without an invite answers 400 `invite_required`; changing it through `PATCH /api/settings` restarts a running endpoint, and a failed restart answers 502 `sync_failed` with the config saved); hubs advertise the user data `blirp-hub`. ALPNs: `blirp/pair/1`, `blirp/sync/1`, `blirp/proxy/1`, `blirp/files/1` (§10a). One accept loop routes by ALPN: a hub accepts pairing from anyone and sync/proxy only from paired, non-revoked machines (`devices` kind `machine`, matched on the TLS-authenticated endpoint id); a node accepts proxy only from its hub. Standalone machines open no endpoint at all.

Wire format (all three protocols): frames of a 4-byte big-endian length + JSON. JSON because replicated payloads are already JSON and stay debuggable. Frames are size-checked before reading (8 MiB hard cap, 64 KiB for handshake/control frames). Each protocol opens with a hello carrying the sender's `versions`; the receiver picks the highest common version or answers `unsupported_version` (current: 1; replication: 3, see Replicated schema below).

Pairing (`blirp/pair/1`):
1. Hub: `blirp hub enable` (or UI) -> invite `blirp1-<base32 ticket>` (JSON `{addr: EndpointAddr, invite_id: 128-bit hex}`) + 8-char code `XXXX-XXXX` from `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (40 bits; no 0/O/1/I) + QR of `blirp://join/<invite>#<code>`. Valid 10 minutes, single use, at most 5 attempts (counted when an attempt starts, so parallel attempts cannot exceed it), then invalidated. Invites live in the hub's memory; a daemon restart invalidates them.
2. Node: `blirp pair <invite> <code>` (or UI). On a LAN, `blirp pair <code>` (empty invite in the API) finds the only hub advertising itself over mDNS and uses that hub's only open invite.
3. Protocol: node `hello {versions, invite_id?, spake}` -> hub `challenge {version, spake}`: symmetric SPAKE2 (spake2 crate, Ed25519 group, identity `blirp/pair/1`) with the normalized code as password. Then key confirmation: node `confirm {mac}`, hub `confirm {mac}` with HMAC-SHA256 keyed by the SPAKE2 key over a transcript hash binding the invite id, both endpoint ids (as authenticated by QUIC TLS) and both SPAKE2 messages; tags are checked in constant time. Only after confirmation both send `meta {name, os, mac}` (MACed with the same key); the hub stores the node and answers `welcome`. Errors are `error {code, message}` (`wrong_code`, `expired`, `too_many_attempts`, `unknown_invite`, `invite_required`, ...).
4. Hub stores the node in `devices` (kind `machine`, `can_control_terminals = 1`: paired machines are trusted to control terminals by default) and `machines`; the node stores `sync.role = "node"`, `sync.hub = <hub id>` in config and the hub's last address in the `settings` key `sync.hub_addr`.

Replication (`blirp/sync/1`): the node dials the hub and opens one bidirectional stream for strict request/response (`hello {versions, machine}` -> `welcome {version, hub_machine_id, head}`, `push {entries}` -> `push_ack {acked}`, `pull {after}` -> `page`); the hub opens one unidirectional stream for `notify {head}` frames whenever `hub_log` grows.

Replicated schema: the sync protocol version (`SYNC_VERSIONS`, negotiated in `hello`/`welcome`) also names the replicated schema, i.e. the rows and fields changes carry. A peer that does not know a field silently drops it from what it pulls (and from what it pushes, where the receiver fills in its default) while its pull cursor moves past the row, so it never gets that field again: 0.1.x nodes pulling the projects a 0.2.0 hub wrote with migration 10 lost `chats` and `merged_into` that way. Rule: a change that adds or changes a replicated column or `Change` field bumps the sync version, and a build speaks only its own version, so hub and nodes of different replicated schemas refuse each other with `unsupported_version` until both run the same release; the hub's error carries its `versions`, which older hubs do not send, so each side knows which machine runs the older release (`SyncError::ReleaseMismatch {peer_older}`). The node keeps its outbox and retries; `GET /api/sync/status` reports `update_needed` (`this_machine` or `hub`; on a hub `this_machine` while a paired machine with a newer release is refused) and, on a hub, `outdated_machines` (paired, non-revoked machines refused for an older release; a refusal is forgotten when that machine syncs, is revoked or its connections are closed, and only non-revoked machines count, for the hub's own `this_machine` too), which `blirp doctor`, `blirp hub status` and Settings > Machines & Sync show as which machine to update; a release that changes no replicated field keeps the version and interoperates. The test `replicated_schema_is_pinned_to_the_sync_version` (blirp-sync) pins to the version the serialized fields of a sample of every `Change` variant with every optional field set (an exhaustive match makes a new variant fail to compile until it has a sample), the TypeScript declaration (ts-rs, docs stripped) of every payload type and of every enum a payload carries (each field whether or not serde skips it, each enum value, since a new value breaks older peers' decoding), and the columns of every table a change writes (`Change::describe`, plus `brief_history`, `deleted_sessions`, `deleted_records`), so neither a new field, variant or enum value nor a migration of those tables gets past it unnoticed. Current: 3 (schema of migrations 10, 14, 16, 17 and 18; 0.1.0 spoke 1, 0.1.1 to 0.2.0 spoke 1 and 2). Rows already damaged before the rule are repaired by re-sending them: migration 12 sets the settings key `sync.requeue_projects` (when there are projects), and the next `Store::set_replication(true)` on a hub or node (every daemon start) queues every project once; the hub's copies reach every node with its next pull, and since `chats`/`merged_into` are sticky and win the tie on equal `updated_at` (§10 conflict rule), a copy that lost them is repaired and never repairs the hub back. Rewinding a node's pull cursor instead would not work: the hub refuses a cursor that went back behind its compacted log (`resync_required`), a replay would re-apply other machines' owned rows over this machine's later writes whose outbox entries are already pruned, and it would re-send every event; project rows are never compacted, but the damaged copies were applied, so only a fresh entry reaches them.

Presence (added in sync protocol version 2; every version spoken now has it): the hub knows which machines have a live sync connection and sends `presence {machines: [{machine_id, online, last_seen}]}` (the hub included) on the notification stream when a machine connects or disconnects and every minute while connected (`last_seen` = connect, disconnect or the latest minute). It is runtime state held in memory, never written to `hub_log` or replicated. A node knows the hub is online while its own connection is up; it forgets the other machines' presence (unknown) while disconnected. `GET /api/machines` adds `online` (null = unknown) and the runtime `last_seen`; a change of who is online emits `sync_updated`, on which clients reload machines.
- Push: node sends outbox entries after `last_pushed_origin_seq` in batches (<= 500 entries or 4 MiB). Hub, in one transaction: first logs its own pending local writes into `hub_log`, then inserts each entry (idempotent: an entry at or below the origin's acknowledged cursor, committed with the log, is skipped, since its row may have been compacted away), applies it to its tables and advances the node's cursor; acks the highest origin_seq. Entries whose payload does not match their declared entity/op/key, or `machines` rows for another machine than the sender, are rejected (logged at warn, never retried). A rejected entry still gets a position marker in `hub_log` (op `marker`, no entity, key or payload; pulls send it only to its origin, as an own entry), so the origin's `own_seen` passes it and it stops skipping the owner's writes of that row (without it, the entry stayed in the origin's outbox and every pulled owner write of the row was skipped until another of its writes was logged). Parking: an entry that changes another machine's session or folder the hub does not have yet (its owner has not synced it, e.g. a rename or merge on the machine that launched a session elsewhere, right after the launch) is not rejected when that owner is a paired, non-revoked machine (only its row can arrive): the hub keeps it in `hub_parked` (with a marker as above), reduced to what another machine may change (a session's title and project with their edit times and its machine; a folder's new project), at most 16 KiB each and 1 000 per origin (more are rejected, other origins are not affected). Once the owner's upsert or delete of that row is applied, at the end of that batch the hub applies what was parked for it in the order it was parked, rebuilt on the stored row and checked as if it arrived then, and queues it as its own write, so it is logged after the owner's row and every machine applies it after that row; the origin gets it back from the hub like any other machine's write. A parked folder re-point (merge) is applied only while the folder is in a project that is the target or was merged into it (`merged_into`, through chains), so a folder its owner filed elsewhere meanwhile stays there. Dropped: what was parked for a row that was deleted, by a machine that is no longer paired (revocation drops its parked entries at once, so does `rebind_machine` for the old id), and after 7 days (`compact_hub_log`). Rows the hub owns itself are never waited for. An entry that fails to apply on the hub (constraint) is still logged (an event is logged without payload, so one the hub could not store is left out of pulls).
- Pull: node requests `hub_log` after `last_pulled_hub_seq` (the hub records that position for compaction, §5). The page carries other machines' entries in full (events read from `events`, compacted markers left out) and the requester's own entries only as position markers, plus `own_seen` (the requester's highest origin_seq logged before the page). The node applies the page and moves its cursor in one transaction. A remote entry whose origin is empty or this node itself is skipped: the node's own entries only ever come back as markers, and such a label would pass every ownership check.
- Ownership (checked by the hub before an entry is logged, and again by a node for every pulled entry, against the entry's origin machine): `project_paths` rows, sessions and events belong to their machine (`machine_id`; an event to its session's machine). Another machine may only re-point an existing folder to another project (merge, `git_remote` unchanged), and for an existing session of the same `machine_id` change its project and title (each kept only where newer, see Conflict rule; status fields are the owner's: only the machine running a session knows it): every other field of such a write (`agent`, `agent_session_id`, `origin`, `cwd`, `worktree`, `transcript_path`, `parent_session_id`, `branch`, `started_at`, `summary_json`, `distilled_through_seq`, tokens, cost, `compacted_at`, `context_near_full_at`, and the status fields `status`, `ended_at`, `last_activity_at`, `exit_code`, `stopped_by_user`) is replaced by the stored value before it is applied and logged, since a foreign copy carries whatever version of them it last saw. No machine removes another machine's folder (`DeleteProjectPath`); a deleted project's folders are dropped by every machine itself when it applies the `Project` change that deletes it. `machines` rows are written by their own machine, or by the hub (pairing, revocation) on a node's pull; `DeleteMachine` is never accepted from another machine. Entries over 4 MiB or with invalid ids are rejected. Records, briefs, wiki pages, resources and projects are shared by design. Rejected entries are logged at warn and never retried; entries waiting for a row the hub does not have yet are parked (Push, above). `DELETE /api/sessions/:id` for another machine's session is forwarded to that machine.
- Conflict rule: shared rows (projects, records, wiki pages, resources, the current brief) keep the newest version by `updated_at` wherever and in whatever order the versions arrive: an upsert replaces a row only when it is newer, ties broken by comparing the remaining columns (a total order, so every machine keeps the same version). A stale copy, e.g. what a machine re-pairing after a while queues, never overwrites a newer edit. A local edit is stamped after the version it replaces (`updated_at` at least 1 ms past the stored one), so a clock that runs behind never loses an edit. Deleted records and sessions have tombstones (`deleted_records`, `deleted_sessions`), written wherever the delete is applied: later writes of them are ignored and a pulled delete always applies. Owned rows (machines, folders) are last-writer-wins by `hub_seq` order: a node skips a pulled remote upsert/delete of such a row it wrote itself later (a local outbox entry for the same entity/key with origin_seq > own_seen: unpushed, or pushed after the remote entry), because that write will be (or was) logged after it. Sessions: every field except title and project is written only by the owner (another machine's write keeps the stored ones, Ownership), so the owner's writes apply in hub order; title and project are edited by other machines too and each keeps its newest edit by its own time (`title_updated_at`, `project_updated_at`; ties by value), whatever write carries it, so the owner's full-row writes (a status tick built before a rename or move reached it) never revert a newer rename or move, on any machine, in any arrival order. A local write stamps a changed title (a move: project) after the stored edit time (also when that came from a machine whose clock runs ahead); a local write built from an older version of the row (its edit time below the stored one) keeps the stored title, and any write that is not a move keeps the stored project. Hence a node never skips a pulled session write, and compaction removes another machine's session write only behind an owner upsert with edit times at least as new (§5). Changes logged before migration 14 carry no edit times (0), so between them the larger value, not the later, would win on a machine replaying the log; a hub therefore gives every session's title and project without a time the time 1 and re-sends the rows once (settings key `sync.stamp_sessions`, `Store::hub_stamp_legacy_sessions` at daemon start), and every machine converges on the hub's values, which followed hub order; edits made since carry the current time and still win. Folders have no such times: another machine only re-points one (merge), and its owner writes a folder only when it assigns it (registration, resolution of a new folder), never as a periodic full-row write, so hub order is kept there. The hub's tables always equal `hub_log` replayed in order. `events` are append-only and keyed by (session_id, seq), except that a session's machine may drop a session's events below a seq (`Change::TruncateEvents {session_id, below_seq}`, entity `event_floors`, owner-only like events, checked by the hub and every node): each machine deletes them and keeps the floor (`event_floors`, only rises), so the change is idempotent and an event below it that arrives later (a replay, an older build of the owner) is ignored; the hub's log keeps the rows of such events, whose pulls then leave them out like those of a deleted session. Used by the one-time Codex subagent repair (§8). A `briefs` change carries its `brief_history` row (unique id, origin machine): the history row is inserted (never overwritten) everywhere, so versions written concurrently on two machines all stay in the history, and the current brief is the newest of them (by `updated_at`, then id). Version numbers are derived when read (1 = oldest by `updated_at`, then id; a new version is stamped after the newest known one); revert takes a history id (or a derived number). Local deletion of an agent transcript never deletes anything (ingest-only).
- Crash safety: every apply commits together with its cursor; re-sent batches are ignored. Offline nodes queue in the outbox; the node reconnects with exponential backoff (1 s .. 60 s, jitter). Local writes are picked up by polling the outbox head every 500 ms.
- Hub itself is also a normal machine with its own sessions; its own writes enter `hub_log` within 500 ms (or before any push/pull is served).

Remote proxy (`blirp/proxy/1`): every node keeps one proxy connection to its hub and either side opens bidirectional streams on it (so nodes behind NAT are reachable). A stream starts with `open {version, target, control, via}` answered by `reply {ok, code?, message?}`; after `ok` it carries plain HTTP/1.1 (including WebSocket upgrades) served by the target daemon's own axum router (hyper over the stream). The hub serves streams addressed to itself and relays others byte for byte to the target's proxy connection (`machine_offline` when it is not connected). `control` is ANDed on the hub with the requesting machine's `can_control_terminals`; a node trusts its hub's value but grants it only when its own config has `sync.allow_hub_control = true` (default false: the hub and other machines can read a node, not control it). Only method, path and body (JSON, or the raw bytes of a terminal upload) are forwarded, never local credentials. Proxied requests run with `admin = false` (§11).
- `POST /api/sessions` with `machine` != this machine is forwarded to that machine; stop/resume/delete of a session of another machine are forwarded too. The launching daemon remembers the session's machine so its terminal can be attached before the row replicates.
- `GET /api/terminals/:id/ws` for a session on another machine is relayed through the hub. Without `control`, terminal input and resize frames are dropped (on both ends). `POST /api/sessions/:id/uploads` is forwarded the same way (raw body, `control` required on both ends).
- `/api/machines/:id/{health,agents,dirs,clone,clone/:job}` for another machine are forwarded to it (the target answers the same route for its own id), so the new-session dialog shows the target's agents (with claude's login state), browses its folders and clones onto it. `clone` with `project_id` is resolved on the requesting machine (the remote URL of its folder of that project) and forwarded as a URL without credentials.

Revocation (`DELETE /api/machines/:id` or `DELETE /api/devices/:id` on the hub): the device and the replicated machine row are marked revoked and the machine's live connections are closed at once; reconnects are refused. `PATCH /api/devices/:id` also closes the machine's connections (or the browser device's WebSockets) so they reopen with the new rights. Leaving (`POST /api/sync/leave` on a node): the node stops its sync session, opens a fresh one, pushes what is still queued (new batches start for at most 5 s) and sends `leave`; the hub revokes the sender (device revoked with terminal control off, machine row revoked; the machine is the connection's TLS-authenticated endpoint id, never an id from the message, so a node can only revoke itself), answers `left` and closes the node's connections. The whole exchange is bounded (10 s); the node then becomes standalone in any case (`sync.allow_hub_control` reset). When the hub could not be told, or changes had not reached it, the answer carries a `warning` asking the user to revoke the machine on the hub. `DELETE /api/machines/:id` on a node is refused (409 `not_hub`).

## 10a. Project files (`blirp::files`, `blirp_sync::files`, `blirp_core::files`)

Design and rationale: [design/project-file-sync.md](design/project-file-sync.md); user guide: [project-files.md](project-files.md). v1 = phases 0 and 1.

- **Root**: one `ProjectPath` on its origin machine; `root_id = hex(blake3("<machine_id>\n<path>"))[..32]`. The hub keeps one tree per root; every working copy (the origin folder, the hub copy for cloud sessions, copies on other machines) writes to it. A root is registered by its origin's first commit (the hub checks the id against the claimed path and that the hub has the `project_paths` row; else `root_pending`, retried).
- **Eligible folders**: this machine's folders of live projects and, for a project without folders, its workspace here once it exists (§5; a root like any folder), except Chats buckets (`projects.chats`, and a pre-Chats Home project), scratch projects (resolution-made, never touched, in a scratch folder per §5), anything else inside `BLIRP_HOME`, and removable or network drives. A workspace root is registered by its path (`.../workspaces/<project id>`: a live, non-Chats project, following `merged_into`), as it has no `project_paths` row; a root's project follows `merged_into` (two steps in listings). A copy of a workspace root goes to the receiving machine's workspace of the root's current project, with no folder row. The engine reconciles its folders on `project_updated` and `session_created`, and when the files API makes a project's workspace (new folders and workspaces upload without waiting for the 10 minute rescan). Replication sends `project_updated` too, for every project whose row or folders a committed batch from another machine changed (a hub's push, a node's pull, `Store::apply_remote`; `Store::on_remote_projects`), so a project deleted or a folder removed elsewhere stops syncing here at once. Upload runs when this machine's `sync.project_files` is on (a hard opt-out) and the project's mode (hub `file_projects`: default/on/off) is not off.
- **Scanner** (`blirp_core::files::scan`): own walk without following symlinks; layers (later wins): 1 VCS folders, `.blirp-tmp-*`, `BLIRP_HOME` (not overridable); 2 build denylist (+ `*.exe` outside `bin/` of non-git roots, `*.zip` over 10 MB); 3 `.gitignore` + `.git/info/exclude`; 4 secrets denylist + private-key header in the first 4 KiB of files under 1 MiB; 5 `.blirpignore` (`!` re-includes; a re-included secret is flagged). Caps `files.max_file_mb` (skip), `files.max_root_gb` and 100 000 files (root paused). Pauses while `.git/index.lock` or `.git/rebase-*` exists. Symlinks are synced as links when relative, inside the root and with `..` only leading the target (after a name, that name could be a link and the text would not say where it goes). Folders that cannot be listed are recorded: nothing below them is read as deleted, and only a path confirmed missing (not found) is deleted.
- **Hash cache** `file_hashes`: `(size, mtime_ns, file_id)` (inode; Windows creation time) -> BLAKE3; a row is trusted only if it was hashed more than 2 s after the file's mtime (racy rule). Hashing runs behind a semaphore of one on the blocking pool.
- **Engine** (daemon, hub and node roles): watcher (notify, 2 s debounce) + rescan at start, every 10 min and after watcher errors. An upload pass diffs the scan against `file_base`: new/changed -> `Put{hash}`/`Link`, gone -> `Delete`, excluded now -> `Forget` (no tombstone; accepted from the origin machine only; a copy marks its base `skipped` and never writes the path again while it is left out there; on a case-insensitive system a file or folder renamed only in case is a `Delete` of the old name, not a `Forget`: every component is compared exactly); the executable bit is kept from the base where the OS cannot see it; per batch of at most 1000 changes uploads that batch's missing blobs (at most 4 streams, `files.upload_kbps` token bucket) and then commits it with the origin's git manifest. A path whose last change the hub refused (`file_base.rejected`) is held (counted as pending, not sent again) until Bring changes here or Update from hub. Watcher events under excluded build folders (below the copy's root) are dropped before they trigger a pass. A registered folder that is not on disk (not found or not a folder: deleted, moved, an unmounted drive, a drive not ready or a network share gone (Windows `ERROR_INVALID_DRIVE`, `ERROR_NOT_READY`, `ERROR_BAD_NETPATH`, `ERROR_NETNAME_DELETED`, `ERROR_BAD_NET_NAME`; unix `ENODEV`, `ENXIO`, `ESTALE`); any other failure to read it, such as a missing permission, is an error, logged when it starts or changes rather than on every pass) is skipped with state `missing`: not watched, scanned or uploaded, no `file_copies` row made for it, while an existing row and its bases stay (a folder that comes back unchanged uploads nothing again; a workspace that synced before stays tracked the same way). A pass that fails because its folder vanished since the last reconcile reports `missing` and asks for a reconcile (not a full rescan). Bring changes here and Update from hub check the disk at request time and refuse a folder that is gone (409 `root_missing`); when the disk and the engine's last reconcile disagree they ask for a reconcile. A missing folder is logged with its path once when it goes and once when it is back, and syncs again from the next reconcile after it is back (at the latest the 10 minute rescan). A missing folder's key is its nearest existing ancestor canonicalized with the rest joined on, so it matches the key it had. What comes back may be an empty folder made in its place (a workspace is made again on demand by the files API and by a session start): a folder seen missing, or whose identity (device and inode; volume serial and file index on Windows) changed since its last settled pass, holds every delete, however few, until a pass holds nothing or the user confirms (`held_deletes`), and a workspace first takes back from the hub the files it synced and lost (as Restore from hub). The identity of a settled pass is stored in `file_copies.identity` (`<device>:<inode>`, migration 15), so a folder removed and made again while the daemon was stopped is caught too (only another inode on the same device counts: a device number can change across a reboot or remount, which alone holds nothing and is recorded again); a row that changes root or origin forgets it. A file larger than the hub accepts (`too_large`, or over the `max_file` the hub announced in the last `Welcome`, which also caps the scan without connecting) fails alone and stays pending; the rest of the folder uploads. A path skipped here (case collision, folder in the way, left out on this machine) that later appears uploads as new (base 0): it conflicts rather than overwriting the hub's version. Mass-delete guard: a pass that would delete every synced file of a folder that has more than one, or at least 10 files and more than 30% of them, commits nothing and the folder shows `held_deletes` until `POST .../files-sync/held` confirms (`delete`: upload with the deletes) or restores (`restore`: write back missing files whose base equals the hub's current version, only while the folder exists). `POST .../held` with `delete` commits only the deletes the folder showed as held; anything that disappeared since waits for its own confirmation. The first start (after upgrade or pairing) waits `files.grace_until` (10 min) while it scans; `POST /api/files/start-now` ends it. Settings key `files.paused` pauses uploads and the automatic apply at session start; the upload that Bring changes here and Update from hub run first obeys the same gate (machine switch, project mode, pause, grace period), and only the apply itself runs.
- **Commit** (hub, one transaction per batch): a change is accepted only if the path's current version equals its `base_version` (0 = never seen). A root's `head` never restarts: deleting a hub copy keeps the `file_roots` row (`deleted_at`) and its head, and only its origin can make it again, under a new `incarnation` with the sequence continuing. The index and commit results carry the incarnation, and a commit names the incarnation its bases belong to: any other current one refuses the whole batch (`root_replaced`) before anything is applied, so only a writer without one (an origin starting over) makes a deleted root again. On `root_replaced` an origin drops its bases and uploads everything; any other copy detaches; mtimes are clamped to a sane range. A write over a tombstone is always accepted (modify beats delete); the same content twice is `Ok` with the current version; a delete with a stale base is a conflict; a losing write is stored at `name.conflict-<machine>-<YYYYMMDD-HHMMSS>[-n].ext` (machine name reduced to `[A-Za-z0-9-]`, at most 10 live per path, older ones tombstoned into history). Every path is checked (`files::path::check`: relative, no `.`/`..`/empty parts, no control characters or backslashes, no VCS component including `.git.`, `.git `, `GIT~1` and NTFS streams, no `.blirp-tmp-`); links must stay inside; `Put` needs the blob (`missing_blob`); a project in mode off refuses the batch (`files_off`). Replaced versions go to `file_history`.
- **Conflicts on the writer**: a copy writes its losing content to the conflict path locally (the hub's copy of it) and takes the winner; an origin folder (upload-only in v1) records the refused content in `file_base.rejected` (`-` for a delete) and does not send it again; a copy that cannot take the winner does the same. `rejected` is only set when the hub kept the content, and such content may be replaced when the hub's changes are applied, but only while the hub's index still has a live entry with exactly that content; otherwise the hub's version is written as a conflict copy.
- **Applying the hub** (Update from hub on a copy, at session start in a copy (bounded 30 s), Bring changes here on the origin, the overlay of a new copy): full index (pages deduplicated by path) vs bases vs the disk; the blobs to write download first, at most 4 at once, each hash once, with progress, and only the writes run under the engine's work lock: unchanged since base (or refused content already kept on the hub) -> overwrite; missing locally -> write (modify wins); changed locally -> the hub's version is written as a conflict copy and the local one uploads over it; tombstones remove only unchanged files; paths the OS cannot hold, Windows symlinks and case-only collisions are recorded as `skipped` and never read as deletes. Of names that differ only in case, the one this copy holds (a synced base, or the file on disk under another case) keeps its place and the others stay on the hub only; nothing is written for them, so copies on several machines never make colliding conflict copies. A collision is looked at again on the next apply. Bases of paths the hub no longer lists (forgotten, or tombstones past retention) stay while the file is unchanged, so they are not uploaded again; a copy that missed a delete whose tombstone expired keeps its file. Writes (`files::write::Target`): parent folders walked from the root without following symlinks, never inside `BLIRP_HOME` unless the copy is a workspace there, temp file `.blirp-tmp-<rand>` fsynced, content verified against its hash, target re-checked against the expectation, then hard link (new files) or rename. On Windows, a target that refuses to be replaced or deleted (access denied) but can still be renamed, as real-time protection leaves files it is scanning for seconds under load (the same state as a running program's image), is first moved aside to `.blirp-tmp-aside.<its name>`, then the new file moved in (the old one comes back if that fails) and the aside renamed to a plain `.blirp-tmp-` name and removed, or left to the scan's sweep of day-old temp files while it is still held. Until then a missing target with its aside is an operation cut short (a crash; an aside whose target is there belongs to one that finished and is discarded, so a later delete never brings it back): every scan under the copy's work lock puts such a file back in place before it reads the folder, so it is never uploaded as a delete (scans outside it, Preview and the grace-period scan, leave it: they could race a write in progress), by a hard link (else a copy into a file created only if missing) that never replaces a file written meanwhile. A target another process holds otherwise (access denied, sharing or lock violation) is retried with a growing pause from one 5 s budget per pass (a read-only target fails at once); when the budget runs out the error code and the target's attributes are logged.
- **Copies** (`POST /api/machines/:id/files/download`, forwarded like clone): destination `~/blirp/<origin folder name>` or an empty/missing folder inside home (folderless: `BLIRP_HOME/workspaces/<project>`); git remote cloned when the manifest has one and git is installed, HEAD checked out when on the remote (else the branch, with a note), then the overlay; the destination is refused while another running download targets it and checked again (empty, no copy row) right before anything is written. The folder row (`Store::add_project_folder`, explicit `project_id`) and the `file_copies` row are written in one transaction (`Store::register_download`), the copy `pending` with the root's incarnation: the engine uploads nothing from it until a complete fresh apply, where the hub wins over what the clone checked out and the clone's files the hub does not know are recorded as they are (version 0), never uploaded as edits. Only then it becomes `on_demand` (uploads live, takes the hub's changes on demand); a download with failed files stays pending until Update from hub completes it. The hub copy for cloud sessions is the same job on the hub. On reconcile, a copy whose root is gone from the hub or whose incarnation changed loses its bases: an origin uploads everything again (making the hub copy anew), any other copy is marked `detached` (files kept, never becomes an origin); copies with no incarnation yet adopt the current one. Reconcile removes only origin folder rows of vanished folders and detaches copies. A folder whose `file_copies` row changes root or origin drops its bases and hash cache. Scans remove this folder's `.blirp-tmp-*` files older than a day.
- **Protocol `blirp/files/1`** (hub only, `authorized()` like sync; connections tracked per machine, so revocation closes them): every bi stream opens with `Open::{Hello, PutBlob{hash, len}, GetBlob{hash, offset}}`. Control stream: `Roots` -> `RootList{roots, project_modes}`, `Index{root_id, after}` -> `IndexPage{entries <= 5000, head, more, incarnation}`, `Have{hashes}` -> `Missing{hash, have}`, `Commit{root_id, root_path?, incarnation?, manifest?, changes}` -> `CommitResult{results, head, incarnation}`, `DeleteRoot`, `SetMode`. Blob bytes: chunks of `[u32 zlen][zstd frame of <= 1 MiB raw]`, `0` ends; decompression bounded per chunk. Uploads append raw bytes to `files/tmp/<hash>.part` (resume at its length; the part is created once the transfer is accepted: on the hub after the quota reservation, on a node after the hub announced the blob, so empty content, which sends no chunk, completes and a refused transfer leaves no part), the hub verifies BLAKE3, compresses (zstd 3), fsyncs and renames into `files/blobs/`; downloads resume from `files/dl/tmp/<hash>.part` (one writer per hash, under a per-hash lock), are verified and then moved to a file of the caller's own, so concurrent downloads of the same content never share a file; every machine's engine removes partial downloads untouched for a day at start and daily. `Notify{root_id, head}` on a uni stream. The writer of a commit is the connection's TLS-authenticated machine. A hub without the ALPN -> `hub_outdated`. The hub's own engine calls the same service in-process (`FileHub::Local`).
- **Quota and GC** (hub): quota `files.hub_quota_gb`, else half the free disk when first run (settings key `files.hub_quota`); usage is a running counter of stored bytes plus running uploads' reservations plus the parts of stopped ones. Every upload reserves its announced length against the quota under a lock (announced lengths over `files.max_file_mb` are refused with `too_large`); one that does not fit first checks whether dropping all history and collecting blobs past their grace period could make room at all (else `hub_quota` at once), then drops the oldest history step by step without holding the reservation lock and checks again after each step. Each upload holds its own reservation (a guard with its own id, so two uploads of the same content never end each other's), which ends when it drops: with the stream, however it ends (a cancelled task included), always after the blob lock is released (the two locks are never held in the other order). A connection serves at most 9 streams at once, a machine holds at most 3 `blirp/files/1` connections. Blobs a writer is told the hub has are touched, and a collection re-checks and deletes rows in one write transaction under the blob lock, so a blob a commit starts using is never removed. Daily: history older than `files.keep_versions_days`, tombstones older than 90 days, unreferenced blobs older than 1 h, parts older than 24 h, orphaned blob files.
- **Delete hub copy**: only while the project's mode is off or its origin is revoked (`files_on` otherwise); entries and history go, blobs with the next GC.
- Logs name paths and counts, never contents. Server event `files_updated` on state changes.

## 11. HTTP API (daemon, axum)

Auth: local clients send `Authorization: Bearer <runtime token>`. The loopback listener takes no cookies: a cookie for 127.0.0.1 is sent to every server on that host whatever its port, so another local program could collect it. The SPA gets the token in the URL fragment (`/#token=<token>`, never sent to a server), keeps it in `localStorage` (per origin, so per port), strips it with `history.replaceState` and sends it as bearer (a token set later by a `hashchange` is taken the same way, then the page reloads); WebSockets, which cannot carry headers, use single-use tickets (`POST /api/ws-ticket {path}` -> `{ticket}`, valid 30 s for that path, `?ticket=` on the upgrade). LAN/portal browser devices use device cookies (§13). All JSON; validation errors (malformed or mistyped JSON bodies, query strings and path parameters) return 400 `{error:{code,message}}` with code `invalid_request`; only a missing JSON content type (415) and an oversized body (413) keep their own status.

Every authenticated request carries a principal: local clients (runtime token or WebSocket ticket) have `control` and `admin`; portal browser devices have `control = can_control_terminals`, `files = can_access_files` and no `admin`; requests relayed by the sync proxy have the proxied `control` and no `admin`. Rights are checked before the request body is read (extractors `Control` / `Admin`), so a caller without them always gets 403:
- `admin` (403 `admin_only`): `PATCH /api/settings` (config.toml, settings values), hub enable/disable, invite, join, browser invites, device and machine revoke/patch, hook ingress, global integration install/uninstall, claude's login token, `POST /api/sessions/:id/open`, `POST /api/daemon/shutdown`, `POST /api/update/check`, `POST /api/update/apply`.
- `control` (403 `control_not_allowed`): every other mutation: launch, resume, stop, distill, rename or delete sessions, worktree removal, machine folder listing and clone, project register/rename/delete/merge, brief, records, wiki, resources and suggestions; plus terminal input and resize, and terminal uploads.
- Reads (every `GET`, the event stream, viewing a terminal) need authentication only.
A portal browser device without terminal control is therefore read-only. `tests/daemon.rs` keeps a table of every mutating route and checks it against a viewer and a controlling portal device.

The loopback listener answers only requests whose `Host` is `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>` (403 `forbidden_host`, DNS-rebinding defense).

`/mcp` is local-only: it is mounted on the loopback listener alone (runtime token, loopback `Host`), not on the LAN portal and not for requests relayed by the sync proxy, where it falls through to the SPA. Remote MCP would need device-authenticated access and is not offered yet. `POST /api/daemon/shutdown` and `POST /api/update/apply` are mounted the same way (loopback listener only, 404 elsewhere): only this machine's own clients may stop or update its daemon.

## 13. Portal and remote browser access

- Local desktop and `blirp open`: `http://127.0.0.1:<port>/#token=...`, bearer token from the SPA's origin storage, WebSocket tickets (§11). No cookie on the loopback listener. The portal's device cookie is scoped to the portal's host and never accepted by the loopback listener; the portal never accepts the runtime token.
- Hub with `portal.lan = true`: axum-server with rustls (ring, TLS 1.2/1.3, ALPN `http/1.1` so WebSockets upgrade) on `0.0.0.0:lan_port`, serving the same router; self-signed cert generated with `rcgen` (SANs localhost, 127.0.0.1, LAN IP) and persisted in `~/.blirp/tls/`, generated again (new fingerprint) when the portal starts on a LAN IP the stored cert does not name or the stored pair is unreadable or mismatched (both files are written to temp names and renamed into place); SHA-256 fingerprint (`AA:BB:...`) in `GET /api/sync/status`. The portal runs while the role is hub and `portal.lan` is set, on `portal.lan_port`; this is applied at daemon start, on hub enable (also when already a hub) and disable, and live on `PATCH /api/settings` (a changed port restarts the listener). A portal that cannot start (port taken) answers 409 `portal_failed`; the saved config is kept. Browser devices log in by opening a one-time link/QR `https://<lan ip>:<port>/device-login?invite=<128-bit token>` (5 min, single use, stored hashed, redemption rate-limited to 10 attempts per minute per client IP) created with `POST /api/devices/browser-invite` on an already-authenticated screen; it creates a `devices` row (kind `browser`, no terminal control) and sets `blirp_device=<random 256-bit token>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=400 days` (stored as SHA-256), then redirects to `/`. The portal accepts only device cookies (not the runtime token). Devices are listed and revocable in Settings > Machines & Sync > Devices; revoking or changing a device closes its open WebSockets. Terminal control from a browser device requires `can_control_terminals`.
- Users with Tailscale can instead run `tailscale serve` in front of the portal port (docs/portal.md); the loopback listener only accepts the runtime token, so it is not a target for browser devices.
- Security headers: CSP (scripts self only, no inline scripts; `style-src 'self' 'unsafe-inline'` for xterm.js; `img-src 'self' data:`; `connect-src 'self' ws://<host> wss://<host>`, plus `http://ipc.localhost ipc:` for the desktop app's IPC on the loopback listener only), `X-Frame-Options: DENY`, `SameSite=Strict` device cookies, CSRF protection via bearer tokens (local), same-site cookies (portal) and the `Origin` check on mutations and WS upgrades.

## 15. Desktop shell (Tauri 2)

- Crate `app/src-tauri` (`blirp-desktop`), bundle product `blirp`, identifier `dev.blirp.desktop`. Its only frontend is a bundled loading/error page (`app/src`); everything else is the daemon's SPA.
- Sidecar `blirp` binary (externalBin, next to the app executable in every bundle). On start: probe runtime.json + `/api/health`; if not healthy run `blirp start` (stderr captured to `logs/desktop-daemon-start.log`, 40 s timeout), then navigate the main window to `http://127.0.0.1:<port>/#token=...`. The sign-in fragment also carries the shell's version (`&app=<version>`). The shell remembers the origin and token it signed the window in with. Every daemon start issues a new token, so on window focus, on reopen (tray Open, a second launch, `blirp`) and on every UI page load it re-reads runtime.json, and when a healthy daemon there has another token or port (a restart: `blirp update`, stop and start, a crash the autostart service recovered) it signs the window in again at the route it shows (`<route>#token=...`; the SPA takes a token from a changed fragment and reloads, and the **Try again** of its "Sign in required" screen reloads the page, which runs the check). On failure the loading page shows the error, the log folder, Retry and Open log folder. On macOS/Linux the daemon is started with the login shell's `PATH` (`$SHELL -ilc`) so agent CLIs are found when the app was launched from the Dock or a launcher. Debug builds (`tauri dev`, clippy, tests) use `target/<profile>/blirp`; `build.rs` drops the sidecar config for them and requires it for release builds.
- IPC: only the bundled page (local origin) may call the app commands `startup_state`, `retry`, `open_logs` (`capabilities/main.json`); the daemon origin (`http://127.0.0.1:*`) may only call `notify` (`capabilities/daemon-ui.json`; the command also checks the caller is the signed-in daemon origin), which shows a native notification through notify-rust (synchronously, so failures reach the caller) and requests user attention when the window is unfocused. The webviews do not deliver the Web Notification API to the OS, so the SPA uses this command whenever `__TAURI_INTERNALS__` is present. On Windows the app registers its identifier under `HKCU\Software\Classes\AppUserModelId` at start, without which Windows drops the toasts of an app not installed by an MSI/MSIX (`blirp uninstall` removes it). The window mirrors the SPA's document title (with its `(n)` attention count) onto the native window title. Navigation is limited to the bundled page and the daemon origin; other http(s)/mailto links and `window.open` go to the default browser.
- Plugins: single instance (a second launch focuses the window and forwards deep links), window state (size/position, not visibility), deep link `blirp://join/<ticket>#<code>` -> SPA route `/settings/sync?join=<ticket>&code=<code>` (queued until the UI is logged in). Any web page can open such a link, so it only prefills the join form; pairing always needs the confirmation dialog (hub id from `POST /api/sync/join/preview`, what the hub may do, an unchecked "Allow this hub to start and control terminals on this machine" box that sets `sync.allow_hub_control`), dialog, opener. On Linux and Windows the app registers `blirp://` for its own executable at startup (script installs have no installer to do it); macOS uses the bundle's Info.plist.
- No updater: script installs update with `blirp update` (§17), which also replaces the app, or its **Update now** in the web UI; installer and package installs (NSIS, MSI, DMG, deb, rpm, Homebrew) have no receipt and update the way they were installed. The web UI shows when a release is available (a dot on the top bar's Settings button, a banner dismissed per version in `localStorage`, Settings > About) and which of the two applies (`self_update`); it polls `GET /api/update` on load and every 3 hours. The version is the logo's tooltip and the last line of the settings navigation.
- Window close hides the window; daemon, sessions and tray keep running. Tray: Open blirp (restarts the daemon if it died), status line, "Close window (sessions keep running)", "Quit blirp (stop daemon and sessions)" (confirm dialog, then `POST /api/daemon/shutdown` and exit).
- Windows bundles ship `conpty.dll` and `x64\OpenConsole.exe` (NuGet `Microsoft.Windows.Console.ConPTY`, pinned) next to `blirp.exe`. portable-pty loads `conpty.dll` by name, which resolves from the executable's directory first, and that `conpty.dll` launches `<its dir>\x64\OpenConsole.exe`; without them the inbox ConPTY is used. The standalone Windows zip and the portable app zip have the same layout.

## 16. Quality bar

- Rust: edition 2024, toolchain pinned in `rust-toolchain.toml` (CI and release jobs install the channel it names), `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`. No `unwrap()`/`expect()` outside tests and provably-infallible cases (comment why). Errors: `thiserror` in libraries, `anyhow` at binary edges, never silently swallowed (log with context). No `unsafe` except where a platform API demands it, with a `SAFETY:` comment.
- Child processes: every one is built with `blirp_core::process::command` (tokio: `Command::from` it), which sets `CREATE_NO_WINDOW` on Windows, because the detached daemon and the desktop app have no console and would open a console window for each console program they start (git, probes, summarizers, helpers). `clippy.toml` forbids `std`/`tokio` `Command::new` elsewhere; PTY children are the exception (the PTY gives them their console).
- Web: `pnpm -C web check` (svelte-check, strict TS, no `any`), `pnpm -C web test` (vitest), `pnpm -C web build`. `pnpm -C web e2e` (not part of `test`) builds the SPA, starts the real daemon on a temp `BLIRP_HOME` and drives the UI with Playwright in the installed Edge (`BLIRP_E2E_CHANNEL` picks another browser, `BLIRP_E2E_KEEP=1` keeps the temp dir and `daemon.log`).
- Every adapter, redaction rule, migration, the distill JSON contract, project resolution, pairing, and replication have tests. An integration test starts a daemon on a temp `BLIRP_HOME`, launches a PTY session running a shell echo, attaches over WS, and asserts snapshot + stream.
- CI matrix: windows-latest, macos-latest, ubuntu-latest.
- Logs never contain transcript text or secrets. Warnings and errors of targets that can repeat one line at steady state (`blirp::log_limit::LIMITED_TARGETS`: swarm-discovery's mDNS sends, iroh, the sync loops, the status tick, keep-awake, the ingest and distill schedulers) are rate limited (info lines, which report state changes, never are): a line (target, level, message and fields) is logged once, repeats within 10 minutes are dropped and counted, and the first one after that is logged with the count appended.

## 17. Distribution and updates

No code signing: installs are command-line first, because files fetched with `curl` / `irm` carry no quarantine or Mark-of-the-Web, so Gatekeeper and SmartScreen do not prompt. Integrity: every download is checked against `SHA256SUMS.txt`, whose minisign signature `blirp update` always verifies with the compiled-in key. The install scripts verify it when the machine has a verifier (minisign, else an OpenSSL 1.1.1+/3 with BLAKE2b-512 and raw Ed25519: most Linux distributions, Homebrew's `openssl@3`, Git for Windows; not macOS's LibreSSL; Windows PowerShell and .NET have neither Ed25519 nor BLAKE2b); otherwise the sums are only as trustworthy as the HTTPS download from GitHub the script itself came from, and the scripts say so. `BLIRP_REQUIRE_SIGNATURE=1` makes them refuse to install without a verified signature. Verifying with the downloaded `blirp` itself would be circular and is not done.

- Release assets (`.github/workflows/release.yml`, draft until published by hand): CLI archives `blirp-<ver>-<target>.tar.gz|.zip` (top folder of the same name; Windows adds `conpty.dll`, `x64/OpenConsole.exe`), desktop app `blirp_<ver>_<aarch64|x64>.app.tar.gz` (`blirp.app`), `blirp_<ver>_<amd64|aarch64>.AppImage`, `blirp_<ver>_x64-portable.zip` (folder `blirp_<ver>_x64-portable/` with `blirp-desktop.exe`, `blirp.exe`, ConPTY), the classic installers, `SHA256SUMS.txt` (sha256sum format, over an explicit list of the expected asset names; a missing or unexpected asset fails the release) and `SHA256SUMS.txt.sig` (minisign, key `packaging/minisign.pub`, secret `TAURI_SIGNING_PRIVATE_KEY`). Only the `sign` job gets the secret: it has no token, checkout or package install, and signs with a minisign release binary pinned by SHA-256; the next job verifies the signature against `packaging/minisign.pub` before uploading it. Jobs get least-privilege permissions, actions are pinned to commit SHAs, release jobs restore no caches, dependency installs run with `--ignore-scripts`, and the workflow only runs for pushed tags, or by hand as a dry run that builds and checks every asset but creates, signs and uploads nothing (never for pull requests). Every archive and installer carries `THIRD_PARTY_NOTICES` (`scripts/third-party-notices.sh`).
- Release discovery (scripts, `blirp update`, the daemon): `GET <base>/latest` or `<base>/tags/v<ver>` with base `BLIRP_RELEASE_BASE_URL` or `https://api.github.com/repos/backyarddd/blirp/releases`. With `GITHUB_TOKEN` requests carry a bearer token and assets are fetched from the asset API URL with `Accept: application/octet-stream` (private repositories); clients never forward the token across the redirect to the storage host.
- `install.sh` (POSIX sh) / `install.ps1` (PowerShell 5.1+): verify `SHA256SUMS.txt.sig` with the release key when they can (above; `minisign -V`, else OpenSSL: BLAKE2b-512 of the file for `ED` signatures, Ed25519 over it and over signature + trusted comment), then each asset against `SHA256SUMS.txt`, install the CLI into `${BLIRP_INSTALL_DIR:-~/.local/bin}` / `%LOCALAPPDATA%\Programs\blirp` and the app into `~/Applications/blirp.app`, `~/.local/share/blirp/blirp.AppImage` (+ `.desktop` entry) or next to `blirp.exe` (+ Start Menu shortcut); add PATH (`--modify-path` on unix: one line marked `# added by the blirp installer`; Windows: user `Path`, REG_EXPAND_SZ kept, `WM_SETTINGCHANGE` broadcast). They write the install receipt `install.json` `{version, install_dir, app, path_entry}` (Windows next to `blirp.exe`, else `${XDG_DATA_HOME:-~/.local/share}/blirp/`). Re-running upgrades in place (a running daemon is stopped, then started again with `blirp start`, so a daemon the autostart service supervised stays supervised).
- `blirp update` (`crates/blirp/src/update/`): only for a binary whose folder matches its receipt. Download `SHA256SUMS.txt` + `.sig`, verify the signature with the compiled-in key (`BLIRP_UPDATE_PUBKEY` at build time replaces it for test builds only), download the CLI archive and, if the receipt lists the app, the app asset, check their SHA-256, stage them next to their destinations; only then stop the daemon (`blirp stop` logic), move each old file aside (`<name>.old`, or `<name>.<ms>.old` while an earlier one is still in use) and rename the new one in (Windows can rename a running exe but not replace it; `*.old` files of known names are removed at the next CLI start), then write the receipt (temp file + rename). All or nothing: if any move or the receipt write fails, every file replaced so far is put back and the receipt keeps the old version. Either way the daemon, if it was running, is started again (the new or the old version) like `blirp start`: through the autostart service if it manages one (launchd `kickstart`, `systemctl --user start`), else `<blirp> daemon --detach`. Semver comparison; no downgrade without `--version`; `--check` exits 0 / 10. Every run except `--check` appends an `UpdateOutcome {from, to, installed, ok, error, finished_at}` JSON line to `logs/update.log`, however it ends (also a failed release lookup, a refusal or nothing to install; `to` null before the release is known; `installed` once the files were replaced, so an error after it is a failed restart).
- Update now (`POST /api/update/apply`): the daemon spawns the receipt's CLI (`install_dir/blirp`, also when the daemon runs as the app's sidecar) with `update --version <latest it reported>` like `daemon --detach` spawns the daemon (own session / process group, Windows `DETACHED_PROCESS | CREATE_NO_WINDOW`, no inherited handles, `BLIRP_HOME` set), so it survives the daemon it stops. On Linux, when the daemon runs under systemd (`INVOCATION_ID`), it runs `systemd-run --user --collect --property=KillMode=process` synchronously (it returns once the transient unit started; a failure is a 500 and allows a new attempt; without `systemd-run` it falls back to the detached spawn) with `--setenv` for `BLIRP_HOME`, `PATH`, `XDG_DATA_HOME`, `GITHUB_TOKEN` and `BLIRP_RELEASE_BASE_URL`, because stopping the service kills its whole cgroup; `KillMode=process` keeps a `daemon --detach` the updater falls back to alive when the transient unit ends. One updater at a time (409 `update_in_progress` until it records an outcome, at most 15 min). The UI then polls `GET /api/update`: a new failed `last_update` while the old daemon still answers is shown; once the daemon was unreachable and answers again, or answers 401 (new token), the page reloads (the desktop app signs it in again; a browser tab needs `blirp open`); after 10 min it says to run `blirp start`. The started update (`before`, target) is kept in the window's `sessionStorage`, so after the reload the page still looks for its log entry (for 2 min; the updater writes it after restarting the daemon) and shows a failure. After an update the banner offers **Restart app** when the desktop shell is older than the daemon (the shell passes its version as `app=` in the sign-in fragment; the SPA keeps it in `sessionStorage`) and **Reload** in a browser whose page was built for an older version (`__APP_VERSION__` < `health.version`, e.g. a portal device whose cookie survived the restart). Restart app navigates to `/desktop/restart` on the daemon's origin; the shell's navigation handler cancels that and calls `AppHandle::request_restart()` (the daemon keeps running). No IPC is exposed to the daemon's origin for it. The check behind it: `GET /api/update` caches the answer a day (an hour after a failure), `POST /api/update/check` reuses one younger than a minute; GitHub's exhausted rate limit (403/429 with `x-ratelimit-remaining: 0`) is reported as such.
- `blirp uninstall`: stop the daemon, `service uninstall`, `hooks uninstall` (all agents, blirp-marked entries only), then delete only known names at the receipt's locations (CLI files, the app and its launcher entry and WebView2 data folder, the app's `blirp://` registration when it points there, the marked PATH line / Path entry, the receipt, then empty folders). A binary without a matching receipt is never deleted. Windows deletes the running `blirp.exe` from a hidden PowerShell that waits for the process to exit. `--purge` deletes `BLIRP_HOME` after confirmation, refusing the home folder, filesystem roots and folders that do not look like blirp's.

## 18. Servers and VPS hubs

A hub on a rented Linux server (docs/vps.md) is the same daemon in the same per-user model; no server mode, no new listener.

- Target: headless Linux, x86_64/arm64, glibc >= 2.35 (Ubuntu 22.04+, Debian 12+), systemd, >= 1 GB RAM (more for cloud sessions). Hub role; agents optional (cloud sessions), logged in headlessly: claude via `claude setup-token` + `blirp agents set-token claude` (§7), codex via `codex login --device-auth` (or API key, copied `auth.json`, SSH-forwarded callback; OpenAI's Codex auth docs).
- Supervision: the `systemd --user` unit of §4 plus logind linger, not a system unit with `User=`: the daemon must run as the user whose agent logins, keys and home the sessions use, and `blirp start|stop|update` already drive the user unit. Root is refused (`install.sh --hub` and `blirp hub setup`): every paired machine can start sessions on the hub, so they must not run as root.
- `blirp hub setup [--lan]` (`cli/server.rs`), each step idempotent: refuse root, and a node (config role, before anything changes) -> daemon not running: write the settings below to `config.toml` first (no mDNS window) -> Linux: if `/run/systemd/system` exists, linger (`loginctl show-user <uid> -p Linger`; else `loginctl --no-ask-password enable-linger <uid>`, else print `sudo loginctl enable-linger <user>`), wait up to 10 s for the user manager (`systemctl --user show-environment`), then `service install`, and if a daemon runs but the unit is not active (started directly, e.g. before linger) `blirp stop` so the unit starts the next one; without systemd or a reachable user manager print why and skip autostart -> `blirp start` -> daemon was already running: one `PATCH /api/settings` (with `base`, only when a value differs) setting `sync.lan_discovery = false` (mDNS would advertise the hub on a provider's shared network and there are no LAN peers) and on Linux `sessions.keep_awake = false` (servers do not sleep); `--lan` (a hub at home) sets discovery true and leaves keep-awake alone -> `POST /api/sync/hub/enable` (idempotent; 409 on a node) -> invite + next steps. `install.sh --hub` = `--no-app` + install + `PATH=<install dir>:$PATH blirp hub setup` (the unit records that PATH).
- Network: nothing inbound. iroh dials out, hole-punches through the server's stateful firewall and falls back to the relay; the endpoint's UDP port is ephemeral, so there is no port to open. The LAN portal stays off; it binds `0.0.0.0` and has no password (one-time login links, device cookies), so on a VPS it must only be reached over a tunnel (SSH forward of the loopback port, or Tailscale/WireGuard with the portal port allowed only on that interface).
- `blirp backup <file>`: `VACUUM INTO` from a read-only connection (a consistent snapshot next to the running daemon; WAL writers are not blocked) into a file created empty with `create_new` and mode 0600, so it never overwrites. `identity.key` and `config.toml` are copied by the user. Updates stay manual (`blirp update`; docs show an optional user timer) because an update restarts the daemon and detaches running sessions.
- `blirp doctor`: role, autostart (`service status`), linger (Linux), and for a hub/node the relay from `GET /api/sync/status` `relay_url` (the endpoint's home relay); and `[warn] sync:` naming the machine to update when sync is refused for another release (§10 Replicated schema); missing autostart or linger on a hub, or no relay, is `[warn]` (does not fail the exit code). A server hub has keep-awake off (above); where it is on, a refused logind lock logs at most once per 10 minutes (§16).
- No Docker image: agents, their logins and `blirp update` belong to a user account; one static binary and a user unit are simpler than an image that has to carry them.
